医疗制造业 PHP 岗位定向面试准备 ​

这份文档把岗位职责和简历中的真实经历对齐。面试时可以使用项目中的事实，但不要把准备案例说成已经交付过的 MES、E-DHR 或 UniApp 项目。

一、岗位匹配结论 ​

岗位要求简历已有证据面试前要补齐的表达
PHP 后端与业务功能CodeIgniter 3、PHP 7.x、SCRM、培训、卡券、O2O、二手车后台用 Laravel 的容器、中间件、队列、事件、策略模式重述实现思路
MySQL 与性能索引、查询、事务、行级锁、主从分离、导出优化能从执行计划、索引、锁等待、分页和归档说明排查过程
系统集成快递 API、微信支付、企业微信、SSO、O+O、微服务网关、Kafka、RocketMQ用统一客户端、幂等、重试、死信、对账和链路日志回答异常闭环
权限与审计RBAC、数据隔离、按钮级权限、JWT、Token 黑名单、AOP 操作日志补充医疗场景中的最小权限、电子签名、审计追踪和权限复核
MES / E-DHR简历未明确写出实际项目只讲可迁移能力，并准备工单、批次、报工、质量和追溯的方案题
Laravel简历主要是 CodeIgniter 3，技能栏写有 Laravel准备 CI3 到 Laravel 的迁移映射和一个可运行的小模块思路
UniApp简历未明确写出实际项目不声称已有生产经验；说明接口、扫码、离线同步和发布流程的学习计划
医疗合规简历未明确写出实际合规项目掌握电子记录、审计追踪、变更控制、验证测试的边界，回答时避免承诺法规结论

二、90 秒自我介绍 ​

我有 3 年以上 PHP 后端开发经验，主线是企业级后台和业务系统。我在 CodeIgniter 3 体系中负责过 SCRM、培训证书、B2B 卡券、门店 O2O 和二手车交易后台，做过 MySQL 查询与索引优化、Redis、RocketMQ、Kafka、第三方 API、RBAC、SSO、审计日志和库存并发控制。

我比较擅长把业务流程拆成状态、字段、权限和接口，再落成可测试的模块。例如卡券项目覆盖生成、审核、发放、兑换和核销；二手车项目涉及多级审批、库存预占、超时释放和多系统同步。近期也在使用 Spring Boot 和 DDD 扩展后端设计能力。

这个岗位的 MES、E-DHR 和医疗生产场景是我需要进一步深入的方向。我的切入点是先把工单、批次、报工、物料、质量和入库链路建模清楚，再通过 Laravel 的服务层、队列、权限、审计和测试体系落地，并和质量、设备、生产人员一起完成联调和验证。

这段介绍的重点是可验证的经历、迁移能力和学习边界。不要把“参与过方案设计”说成“已经通过某项审计”。

三、把简历项目讲成岗位需要的能力 ​

1. 二手车后台：最适合回答流程、并发与集成 ​

用 STAR 结构回答：

  1. 场景：100+ 门店、多级审批、订单和库存同时变化。
  2. 任务：既要支持门店差异化价格审批，又要防止并发下重复占库存。
  3. 行动：用库存预占、15 分钟超时释放和数据库行级锁控制库存；用审批状态和价格阈值路由流程；统一封装 HTTP 客户端、重试和日志追踪。
  4. 结果：审批流转效率提升约 60%，高并发场景下避免超卖，支持万级数据导出。

可迁移到 MES 的说法：工单释放、报工提交、物料扣减和入库确认也要分别建模状态，不能只依赖一个 status 字段覆盖所有业务含义。

2. SCRM：最适合回答消息、性能与数据安全 ​

  • 日均消息推送超过 10 万条，使用 RocketMQ 做异步任务。
  • 通过 SQL 查询和内存管理让 API 响应时间缩短约 40%。
  • 数据脱敏方案通过企业安全合规审核。

面试追问时要补出：消息唯一键、消费幂等、失败重试上限、死信处理、积压监控、敏感字段展示和日志脱敏规则。

3. 卡券和物流：最适合回答生命周期与第三方接口 ​

卡券从批量生成、审核、发放、兑换/核销到售后，天然适合说明状态机；快递查询和云打印适合说明适配器、超时、重试、限流和对账。这里可以自然过渡到 ERP、OA、MES 接口，但要明确这是能力迁移，而不是简历中已交付的 MES 项目。

四、最容易被追问的四个差距 ​

Q1：你的简历主要是 CodeIgniter，为什么能做 Laravel？ ​

两者的 MVC 和请求生命周期不同，但业务拆分能力是共通的。我会把已有的控制器逻辑拆成 Form Request 校验、Service 业务服务、Repository 或 Query Object、Job 队列任务和 Event 事件。Laravel 的服务容器负责依赖注入，中间件负责认证和权限，队列负责异步接口，Policy 或 Gate 负责资源授权。入职后我会先按项目现有约定完成一个小模块，再补测试和文档，避免直接按个人习惯重构。

Q2：你是否做过 MES 或 E-DHR？ ​

我的简历没有把 MES 或 E-DHR 作为已交付项目，我不会把其他后台项目包装成医疗项目。但我做过状态流转、库存并发、权限数据隔离、第三方接口、异步消息和审计日志，这些能力可以迁移到工单、批次、报工和电子记录场景。我已经按生产链路准备了字段、接口、异常、测试和追溯方案，入职后会先跟业务确认实际流程和质量要求。

Q3：怎样保证生产数据可追溯？ ​

每条关键记录都保留业务主键、来源系统、来源单号、批次、操作者、设备、事件时间、入库时间、版本和关联审计记录。写入使用幂等键，状态转换有白名单，关键动作写不可变事件和前后值。跨系统发送用 outbox 或可靠消息，定时做数量和状态对账，异常进入可重试队列并由人工闭环。

Q4：医疗系统上线前怎么验证？ ​

先把需求、风险、字段和权限写成可追踪的验收点；开发阶段做单元和接口测试，联调阶段覆盖正常、重复、超时、断网和权限边界；上线前按受控版本完成测试记录和缺陷关闭。涉及电子记录的功能，还要验证审计追踪、签名绑定、时间、备份恢复和权限复核。具体法规适用范围由质量和法规团队确认，开发人员不单独作合规结论。

五、入职前的最小准备清单 ​

  • Laravel：路由、中间件、Form Request、Service Container、Policy、Queue、Event、Cache、Eloquent 事务和 PHPUnit。
  • MySQL：联合索引左前缀、EXPLAIN、事务隔离、死锁、SELECT ... FOR UPDATE、按业务键幂等。
  • 集成：OAuth2/JWT、签名、超时、重试退避、幂等、死信、对账和结构化日志。
  • MES：工单释放、工序、报工、物料消耗、质量检验、批次拆分/合并、入库和召回追溯。
  • E-DHR：电子记录版本、审计追踪、电子签名、权限复核、变更控制和验证证据链。
  • UniApp：扫码报工、网络状态、SQLite 本地队列、冲突处理、断点重试和小程序/APP 发布差异。
  • 沟通：每个需求都输出目标、范围、字段、状态、权限、接口、异常、验收和上线回滚点。

六、反问面试官的问题 ​

  1. 当前 MES、ERP、OA、E-DHR 的主数据分别由哪个系统负责？
  2. 工单、批次、报工和质量记录的唯一标识及对账机制是否已经统一？
  3. 系统目前采用 Laravel 的哪个版本，队列、缓存、权限和接口文档使用什么方案？
  4. 设备接入主要是 Modbus、OPC UA、MQTT 还是由设备网关统一转换？
  5. 电子记录和审计追踪由哪个质量流程批准，开发需要提供哪些验证证据？
  6. 上线发布是否有测试环境、变更单、回滚方案和运行监控门禁？

七、不要主动承诺的内容 ​

  • 不要把 CodeIgniter 项目改称 Laravel 项目。
  • 不要把准备中的 MES/E-DHR 方案改称已经通过医疗审计。
  • 不要把“熟悉 UniApp”写成已经独立交付小程序和 APP，除非能拿出真实项目证据。
  • 不要直接承诺 FDA、ISO 13485 或中国法规合规；应说明会按公司质量体系和法规团队确认后的需求实现并留存证据。
