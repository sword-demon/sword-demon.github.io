# herdr、T3 Code 与 Orca：AI 编码工具的区别、痛点与选型

当你开始同时使用 Claude Code、Codex 等编码代理，问题会逐渐从“哪个模型更会写代码”，变成一组更具体的麻烦：终端开得太多，不知道哪个任务在等确认；SSH 断开后不确定任务还在不在；多个代理修改同一份代码；代码写完了，还要在聊天、浏览器、Git 和 PR 页面之间反复切换。

herdr、T3 Code 和 Orca 都在处理这些麻烦，但它们的出发点不同：

- **herdr：围绕终端运行和组织代理，重点是会话持续运行、状态可见与多机器管理。**
- **T3 Code：给不同编码代理提供统一控制界面，重点是对话、权限确认、Git 和跨设备操作。**
- **Orca：把代理放进完整开发工作区，重点是并行任务、审查、浏览器反馈和外部任务自动化。**

如果你熟悉终端、希望保留 CLI 原貌，可以先试 herdr；如果主要烦恼是多个代理界面割裂，可以先试 T3 Code；如果需要把任务从接单、执行一路推进到审查和交付，可以先评估 Orca。

> 名称说明：这里的 Orca 指 [stablyai/orca](https://github.com/stablyai/orca)，官网是 [orca.dev](https://orca.dev)，不是 OCR 工具，也不是其他同名项目。`ocra` 在本文按 Orca 的拼写误差处理。
>
> 核对日期：2026-11-24。功能依据来自文末列出的官方 README 和文档，优缺点及选型建议属于基于这些机制的分析。本文没有进行三款软件的安装实测、性能跑分或稳定性对比；上游更新较快，安装前应再看当前发行说明。

## 先分清：模型、编码代理和管理工具

这三个层次解决的问题不同：

| 层次 | 主要职责 | 例子 |
| --- | --- | --- |
| 模型 | 理解需求，生成推理结果和代码 | 编码代理背后调用的模型 |
| 编码代理 / harness | 提供读写文件、执行命令等工具，组织模型与工具的交互循环 | Claude Code、Codex 等 |
| 管理与工作区工具 | 组织会话、机器、工作区、权限确认、审查与协作入口 | herdr、T3 Code、Orca |

T3 Code 的官方 FAQ 明确说明：它使用现有 harness，自身不是 harness。herdr 则强调管理代理所在的终端，不替换你原本运行的 CLI。Orca 也允许使用现有 CLI 代理，并在外围提供工作区和自动化能力。[1][3][4]

因此，换用这些工具，主要改善的是**人和代理协作的效率**。如果问题出在需求不清、上下文不足或底层模型能力上，仅仅换一个管理界面，不会自动让代码变正确。

## 一张表看懂主要区别

| 比较维度 | herdr | T3 Code | Orca |
| --- | --- | --- | --- |
| 产品出发点 | 代理所在终端的运行时与组织方式 | 编码代理的统一控制界面 | 面向代理的开发工作区与自动化环境 |
| 主要操作对象 | space、终端、pane、机器和代理状态 | 项目、thread、provider、权限与 Git 变更 | 工作区、worktree、代理、浏览器、任务和 bot |
| 典型交互 | 保留 CLI/TUI，分屏操作；另有桌面应用 | 桌面、Web、手机上的统一对话界面 | Chat 与原始 CLI 切换，配合工作区面板 |
| 多机器 | 保存 SSH 机器，汇总代理列表，独立重连 | server 执行代理，客户端远程连接；支持 LAN、Tailscale、T3 Connect | Remote Orca Server、SSH 主机、每工作区云 VM 等运行方式 |
| 并行工作 | 代理可通过 CLI / socket API 创建 pane、互相提示和等待 | thread 可使用独立 worktree；支持代理间任务交接 | coordinator 可拆分任务并创建独立工作区中的 worker |
| 审查与交付 | 核心定位偏终端；可通过插件扩展工作流 | 内置 diff、commit、push、PR 操作 | 行级 diff 批注、Git/PR 工作流，并可把检查失败和评审意见交回代理 |
| 跨设备 | 核心提供多机器终端管理；手机体验需区分具体客户端或插件 | 官方桌面、Web、iOS、Android 客户端 | 官方桌面与移动应用，支持远程回应代理 |
| 更突出的一点 | 会话持续运行、状态汇总、保留终端习惯 | 多代理、多设备操作的一致性 | 从任务入口到执行、反馈与交付的整合 |
| 源码许可 | 核心仓库 Apache-2.0 | MIT；品牌使用另有要求 | MIT |

这张表比较的是产品重心，不能把某一列没有展开的能力理解为“完全不支持”。例如 herdr 有桌面应用和插件生态，T3 Code 也支持 worktree 与代理协作，Orca 也能直接运行原始 CLI。[1]—[5]

## herdr：先把终端里的代理管清楚

### 主要解决哪些痛点

**第一，客户端关了，任务也跟着断。**

herdr 把终端放在后台 server 中运行。退出客户端或丢失 SSH 连接时，只要承载任务的 server 和机器仍在运行，工作可以继续。之后重新连接，回到原来的终端环境。[1]

这里必须分清两个边界：**客户端断开不等于进程终止；机器重启后的会话恢复，也不等于原来的进程存活。** 官方说明，server 或机器重启后可以恢复保存的布局，并恢复受支持的代理会话，但原进程不会跨重启存活。桌面应用还明确区分了“关窗口”和“关 pane”：前者保留运行，后者会结束对应终端。[1][2]

**第二，同时跑了几个代理，却不知道哪个在等人。**

herdr 汇总代理状态，让你看到 working、blocked、idle 等状态。桌面应用还区分了“在你看别处时已经完成”和“你已经看过的空闲状态”。这能减少逐个翻终端确认进度的次数；不过状态能力仍依赖代理的上报或集成，不能把任意终端程序都当作状态识别完整的代理。[1][2]

**第三，本地和远程服务器上的任务分散。**

它能把多台机器放进同一个操作界面，统一查看代理列表。对于经常让代理在开发机、VPS 或远程算力机器上执行任务的人，价值是少记几层“哪台机器、哪个终端、哪个任务”的对应关系。

### 优势

- **保留现有 CLI 工作方式。** 原本的命令、TUI 和终端输出仍是工作入口，对习惯命令行的人迁移成本较低。
- **把运行与显示分开。** 关闭客户端后继续运行、断线重连等能力直接对应长任务的需要。
- **便于程序化协调。** CLI 和 socket API 允许代理创建 pane、向其他代理发提示并等待状态，适合把已有终端流程串起来。
- **核心分发简单。** 核心 README 强调单个 Rust 二进制、运行于已有终端；另有独立桌面应用，不能将整个 herdr 产品范围概括为“只有 TUI”。[1][2]

### 代价与边界

- 如果你真正需要的是可视化 diff、浏览器反馈和 PR 审查，终端管理本身不能包办这些步骤；可能还要配合编辑器、插件或其他工具。
- pane 越多，任务边界越重要。创建多个终端不会自动给每个代理隔离 Git 工作目录，也不会自动解决代码冲突。
- 不同 CLI 的交互差异仍然存在。保留原生终端体验，也意味着你需要理解各个代理自己的命令和权限行为。
- 桌面应用的 mods 被官方视为受信任代码，并非沙箱扩展；扩展能力带来可定制性，也带来需要自行审查的执行权限。[2]

**适合：已经喜欢终端，但受够了管理大量终端与远程任务的人。** 如果你目前只运行一个代理，且现有 tmux 流程很顺畅，herdr 的新增价值主要要看状态汇总和多机器体验是否能节省时间。

## T3 Code：给不同编码代理一个统一操作入口

### 主要解决哪些痛点

**第一，换一个代理，就要换一套界面和操作习惯。**

T3 Code 在同一界面中驱动本机已安装并配置好的代理，官方列出了 Claude Code、Codex、Cursor、OpenCode 等，并提供 ACP 代理接入。它也支持在线程中切换模型，以及让一个代理把任务交给另一个代理。[3]

这里的“统一”主要是操作入口。权限模式和功能细节仍受 provider 影响，官方权限文档就列出了不同代理对各模式的支持差异。不能因为界面一样，就假定底层行为完全相同。[6]

**第二，离开电脑后，任务卡在一次确认上。**

桌面、Web 和手机客户端可以连接同一个 server，查看相同线程并回应代理。对“任务大部分时间可以自主执行，但偶尔需要我确认”的工作，这比回到电脑前再继续更方便。

手机承担的是遥控器角色。真正执行代码的机器仍要开机、在线；如果任务跑在笔记本本机，手机连接不会让睡眠中的电脑继续执行。[4]

**第三，代理完成后，还要手动串起 Git 操作。**

T3 Code 支持每个 thread 使用独立 worktree，并提供 diff、提交、推送和创建 PR 的操作入口。它把“对话中的任务”和“这个任务产生的代码变更”放得更近。[3]

### 优势

- **适合经常切换代理。** 会话、权限确认和 Git 操作有共同入口，减少工具切换成本。
- **跨设备路径明确。** 官方提供桌面、Web 和移动应用，远程连接可选择 LAN、Tailscale 或 T3 Connect。
- **复用已有代理配置。** 不要求通过 T3 Code 购买模型 token；可以使用已有订阅，也有独立 provider 实例和 API 配置方式。[3][4]
- **Git 操作贴近任务。** 对主要通过对话推进开发、完成后集中看 diff 的用户，这种组织方式比较直接。

### 代价与边界

- **多了一层需要兼容的系统。** 出问题时，可能要分别检查代理本身、适配层、server 和客户端，不能把所有报错都归因于模型。
- **统一界面不保证所有原生功能同时可用。** 新 CLI 功能能否出现在界面里，需要看对应适配和 provider 文档。
- **跨代理交接仍需要任务说明。** 即使界面允许切换，也不代表两个代理的内部会话状态、工具语义和权限机制完全等价。交接时仍应写明目标、已改内容、测试结果和未解决事项。
- **免费软件仍有外部成本。** 模型订阅/API、远程机器及可能变化的连接服务政策，都要纳入考虑。官方 FAQ 在本次核对时说明 T3 Connect 当前免费但存在机器数量限制，也保留未来调整的可能。[4]

**适合：已经使用多个编码代理，希望通过统一界面和手机接续工作的人。** 如果只想保持某个 CLI 的原始终端交互，需要先验证它在 T3 Code 中的适配是否满足自己的高频操作。

## Orca：围绕任务组织完整开发工作区

### 主要解决哪些痛点

**第一，代理写代码、人审查代码，需要在很多工具间来回跳。**

Orca 把代理、终端、浏览器和 diff 放进可分屏的工作区。你可以对具体变更行留下意见，再把意见发回代理；也可以在内置浏览器中选中元素，获取 HTML、样式和 selector，作为修改需求的上下文。[5]

这类能力对前端任务很有价值。例如“按钮位置不对”容易产生歧义，而元素信息加上具体要求，可以缩小代理需要猜测的范围。不过传递页面信息不等于已经完成交互测试和视觉验收。

**第二，一个大任务需要多个代理并行推进。**

Orca 提供 coordinator/worker 编排和并行 worktree：协调代理拆分任务，让 worker 在独立工作区执行，再汇总结果。它把“开几个终端并行干活”进一步组织成了带任务关系的工作流。[5]

独立 worktree 可以避免多个代理直接覆盖同一工作目录，却不能避免逻辑冲突。两个 worker 分别修改接口两端，依然需要约定数据结构，并在合并后执行整体验证。

**第三，任务来自 Slack、Linear 或 GitHub，还要人工搬到开发环境。**

Orca Bots 的官方定位是从这些外部入口接收任务，使用你自己的 Claude Code 或 Codex 执行，并让你回到 Orca 审查或接管。README 还列出了定时与事件触发、GitHub/Linear 任务入口，以及把失败检查和 PR 评论交回代理的能力。[5]

这部分能力的价值在于减少任务流转，而不是仅仅让聊天窗口更好看。是否自动提交、推送或创建 PR，应结合具体 bot 配置、权限和团队流程确认。

### 优势

- **任务执行与验收放在同一工作区。** 代码、页面、diff 和反馈之间的距离更短。
- **并行任务有明确的组织单位。** worktree 与 worker 比临时堆叠终端更容易表达任务边界。
- **能接入已有协作流程。** 对经常从 issue 或聊天中领取任务的人，外部入口和自动化比单纯增加模型选择更有用。
- **兼顾 Chat 和原始 CLI。** 官方提供两者间切换的工作方式；但“能在终端运行任意 CLI”与“每个 CLI 都有同等深度的原生 Chat 集成”是两回事。[5]

### 代价与边界

- **需要理解更多概念。** 工作区、worktree、worker、远程运行、bot、插件与自动化都有配置和维护成本。只做简单单线程任务时，收益可能不足以覆盖这些成本。
- **并行会放大资源消耗。** 不同 worktree 中的依赖目录、构建产物和开发服务会占用磁盘、内存及端口；多个代理也可能同时消耗模型额度。
- **外部自动化扩大了权限范围。** 从外部任务入口触发代码修改，需要明确仓库范围、凭据、可执行操作及人工接管点，不能直接把桌面上的权限习惯照搬过去。
- **工具整合不代表结果可信。** bot 返回“测试通过”后，仍应查看具体执行的测试及其覆盖范围；完整交付还取决于需求、测试和审查质量。

**适合：希望把多任务开发、代码审查、页面反馈与团队任务入口集中起来的人。** 如果你的工作流长期只需要“发提示词、看 diff”，可以先用更少的能力开始，再按实际需要启用自动化。

## 三者都无法自动解决的四个问题

### 1. 多开代理，不一定更快

并行收益取决于任务能否独立拆分。可以把总耗时粗略理解为：

```text
总耗时 ≈ 最慢并行任务的耗时 + 协调耗时 + 集成验证耗时 + 返工耗时
```

这只是帮助判断的近似式，不是性能测量结果。如果几个代理反复修改同一个公共接口，协调和返工很可能吃掉并行收益。

### 2. worktree 隔离文件，不隔离整个运行环境

Git worktree 为同一仓库提供独立检出目录，但数据库、端口、外部账号和服务可能仍然共享。两个任务各自在独立目录里启动应用，也可能争用同一个端口、修改同一个数据库。

因此，要区分“代码目录隔离”和“运行环境隔离”；需要后者时，才进一步配置不同数据库、容器或 VM。

### 3. 本地运行，不代表数据完全不出机器

代理使用云端模型时，必要的上下文仍可能发往模型服务商；远程连接、遥测、外部集成和插件也各自涉及数据路径。选型时需要分别检查这些路径。

例如 T3 Code FAQ 说明其代码和提示词由运行机器发往 provider，同时披露产品使用遥测和关闭方式；herdr 桌面应用也披露了默认遥测及 mods 的信任边界；Orca README 则链接到独立的隐私与遥测文档。[2][4][5] 不能只凭“开源”或“本地”两个词判断全部数据行为。

### 4. 界面一致，不代表权限语义一致

相同的“自动”或“完全访问”名称，在不同代理中可能映射到不同能力。选型时应实际试一次命令确认、文件修改和子任务审批，尤其要核对所安装版本的默认模式。[6]

## 怎么选：先看哪一步最浪费时间

| 你最常遇到的问题 | 优先试用 | 试用时重点检查 |
| --- | --- | --- |
| SSH 断开、终端太多、不知道谁在等回复 | herdr | 断线重连、状态识别、跨机器定位是否可靠 |
| 经常切换 Claude Code、Codex 等代理 | T3 Code | 高频功能是否适配，权限和上下文交接是否清楚 |
| 想从手机回复或确认，让远程任务继续 | T3 Code 或 Orca | 连接方式、通知、审批操作，以及执行机器能否持续在线 |
| 多个功能分支同时推进，还要集中审查 | Orca 或 T3 Code | worktree 创建、diff 审查、完成后清理和集成验证 |
| 经常做前端页面，需要把具体元素反馈给代理 | Orca | 浏览器选取元素到代理修改的过程是否减少沟通 |
| 任务主要来自 GitHub、Linear、Slack，想减少人工搬运 | Orca | 触发规则、仓库权限、执行结果和人工接管方式 |
| 只有一个代理，现有终端或编辑器已经顺手 | 暂时沿用现有工具 | 先记录真实阻塞，再决定是否增加管理层 |

如果没有明显偏好，可以拿同一个小任务分别试用，例如：**修复一个页面问题，补充必要验证，查看 diff，最后整理提交。** 不必一上来迁移全部仓库。

建议记录以下指标：

1. 从打开项目到代理开始工作的时间。
2. 发现代理正在等待确认的时间，以及遗漏次数。
3. 从定位问题到发出有效反馈，需要切换多少次窗口。
4. 从代理宣布完成到你确认结果可交付，需要多少时间。
5. 多任务结束后，清理 worktree、服务进程和资源有多麻烦。

这些指标比功能数量更接近实际收益。herdr 的价值通常体现在“任务还在跑，而且我找得到它”；T3 Code 的价值通常体现在“换代理、换设备时少折腾”；Orca 的价值通常体现在“任务、代码、页面和评审意见能在同一流程里推进”。选择与你当前主要损耗相对应的工具，才更容易得到持续收益。
