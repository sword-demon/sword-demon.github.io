# Go 主机安全面试：Linux 挂载命名空间与路径遮蔽检测

同一个 `/etc`，在宿主机、容器和某个服务进程看来，可能不是同一棵目录树。攻击者或受入侵进程可以在自己的挂载命名空间里 bind mount 一个目录覆盖敏感路径，让后续操作看到替代内容；容器运行时和部署系统也会合法地大量使用挂载。面试官通常会追问：Agent 如何判断“路径变了”还是“挂载视图变了”？怎样把行为归因到进程，同时避免自己的 Go 采集器误入目标 namespace？

## 岗位场景

```text
容器内服务或 Web RCE 子进程
  -> unshare / setns 建立或加入挂载命名空间
  -> mount / move_mount 覆盖敏感目录或改变挂载关系
  -> 原路径名仍然存在，但进程看到的对象或内容已经改变
  -> Go Agent 读取目标进程 mountinfo 并核对 namespace 身份
  -> 关联进程、挂载操作、敏感路径和后续执行
  -> 区分容器编排、发布操作与可疑路径遮蔽
```

挂载命名空间隔离的是进程看到的挂载列表，不是全局文件系统的另一种名字。一次挂载变更默认不会影响其他独立命名空间，但挂载传播属性可能让事件在相关挂载间传播。因此，不能只根据路径字符串或一次 `mount()` 调用就下结论。

## 高频面试题

### 1. 挂载命名空间如何造成“同一路径、不同对象”？

**简洁答案：** 每个挂载命名空间有自己的挂载视图。bind mount、独立挂载或覆盖挂载可以让进程在相同路径下看到不同的文件系统或目录内容；路径字符串本身不足以标识它实际看到的对象。

**关键知识点：**

- `unshare(CLONE_NEWNS)` 可创建新的挂载命名空间；新命名空间最初复制调用者的挂载列表，之后的改动通常彼此隔离。
- bind mount 可以把另一目录树接到目标路径上，遮蔽该路径原本可见的内容。
- shared、slave、private 等传播属性影响挂载和卸载事件是否传播，不能把“namespace 隔离”简化为绝对不传播。
- `/proc/<pid>/root` 和 `/proc/<pid>/mountinfo` 提供目标进程视角的线索；读取受权限、进程生命周期和 procfs 配置影响。

**Go 落地思路：**

- 文件事件关联 `pid + process_start_time + mount_namespace_id + mount_id + path`，不要只按 `path` 去重或判断策略。
- 主机级 Agent 优先读取目标进程的 procfs 视图并保留采集时间；读不到时标明上下文未知，不静默套用 Agent 自己的路径视图。
- 对敏感目录建立路径基线时，同时记录它所在的挂载和命名空间上下文。

### 2. `/proc/<pid>/mountinfo` 应该怎样读？哪些字段容易被误用？

**简洁答案：** 每行描述该进程视图中的一个挂载，字段包含 mount ID、parent ID、设备号、文件系统内根目录、挂载点、挂载选项、可选传播信息，以及 `-` 后的文件系统类型、来源和超级块选项。

**关键知识点：**

- 路径中的空格、制表符、换行和反斜线会以八进制转义形式出现，例如 `\040` 表示空格。先分字段再解码；先对整行解码会把路径里的空格误认成字段分隔符。
- `root` 与 `mount point` 含义不同：前者是该文件系统中挂载到此处的子树，后者是当前视图中的挂载位置。
- mount ID 标识挂载，并且卸载后可能被复用；不能单独当作跨主机、跨时间的永久文件身份。
- mountinfo 是读取时的快照，不是完整事件日志；两次快照之间的短暂挂载可能观察不到。

**Go 落地思路：**

- 用 `bufio.Scanner` 或有明确行长上限的读取器逐行解析；先按字段分隔符 ` - ` 分成左右两段，再按各段语法解析，不要把整行直接 `strings.Fields` 后假设可选字段固定。
- 对路径字段中的 `\040`、`\011`、`\012`、`\134` 做一次解码；未知可选字段应跳过，必要字段缺失或过长行才返回可观测错误。保留原始字段以便排障。
- 以 namespace、进程根视图、mount ID 和采样批次关联快照。mount point 相对于该进程的根目录；相同 namespace 内不同 `chroot` 的进程也不能直接复用路径字段。

### 3. 怎样发现敏感路径被 bind mount 或覆盖？

**简洁答案：** 将敏感路径与同一进程视图下的 mountinfo 快照比较，检查该路径处的挂载边界、文件系统来源和挂载根是否发生变化，再结合变更主体和后续行为判断风险。

**关键知识点：**

- 挂载点下方原有内容可能仍在，只是暂时不可见；卸载覆盖层后它可能重新出现。
- 容器 overlayfs、bind mount、只读根文件系统和正常发布都可能造成挂载结构变化。
- 目标路径不一定恰好是 mount point：要判断路径是否落在新增挂载点的子树中。同一挂载点可能存在多层挂载，还要用 parent ID 关系识别当前可见的顶层。
- 可疑度来自上下文组合，而不是“出现 bind mount”这个事实本身。

**Go 落地思路：**

- 维护敏感路径前缀与快照中挂载点的最长路径边界匹配，避免 `/etc` 错误匹配到 `/etc-old`。
- 比较前后快照中的 namespace 身份、mount ID、挂载点、root、文件系统类型、来源和传播标记，并为差异保留时间戳。
- 将“覆盖 `/etc/ld.so.preload` 所在目录后执行异常二进制”等多步链路提高优先级；单独的容器初始化挂载先进入基线或低级别观察。

### 4. Go Agent 怎样把挂载变化归因到进程？

**简洁答案：** 用系统调用或内核事件捕获挂载相关操作作为实时线索，再通过进程身份、namespace 身份和前后快照补充对象关系。单次全量扫描不能可靠回答“是谁做的”。

**关键知识点：**

- `mount`、`umount2`、`setns`、`unshare` 等行为有助于建立时间线，但采集源和内核版本会影响覆盖范围。
- mount 系统调用的参数表达目标和来源意图，不一定等于成功后的最终挂载结构；必须结合返回结果或后续状态核验。
- PID 会复用，短生命周期进程也可能在扫描前退出；仅用 PID 关联容易串错主体。
- audit、eBPF 与周期性 procfs 快照在时效、权限、覆盖面和开销上不同，没有一个来源在所有系统都保证完整。

**Go 落地思路：**

- 标准化事件保留 `pid`、进程启动时间、父进程、uid、namespace 身份、原始操作、返回状态和事件时间。
- 事件触发敏感 namespace 的定向快照；周期扫描用于发现采集启动前的既有状态和补偿缺口。
- 上报 `source`、能力状态、丢失计数和快照时间，让下游能区分“未发生”和“未观测到”。

### 5. Agent 是否应该 `setns` 到目标进程后再检查文件？

**简洁答案：** 通常先通过 `/proc/<pid>/mountinfo` 和 `/proc/<pid>/root` 获取目标视图线索；为检查而贸然让常驻 Agent 的 goroutine 调用 `setns` 风险很高。确需进入时，应隔离在专用、可恢复的线程或辅助进程中，并验证权限和退出路径。

**关键知识点：**

- `setns` 改变的是调用线程的 namespace 上下文；Go goroutine 默认可能在不同 OS 线程间调度。
- `runtime.LockOSThread` 可固定 goroutine 与 OS 线程的绑定，但不会保存或恢复 namespace。进入 mount namespace 还受到 capabilities 与 `CLONE_FS` 共享状态限制，固定线程不能消除这些限制。
- procfs 读取也可能受权限检查、目标退出、PID 复用和访问时序影响。
- 采集失败需要报告“不可见/权限不足/进程已退出”，不能伪装成目标路径不存在。

**Go 落地思路：**

- 常驻采集默认不在通用 worker 上执行 `setns`；优先使用目标 PID 的 procfs 入口完成只读检查。
- 若产品确实需要 namespace 内解析，使用独立受控的辅助进程，限制权限、请求超时和返回字段，并在调用前后校验目标进程身份。
- 对 namespace 切换与恢复做失败路径测试；不把 `LockOSThread` 当作隔离边界。

### 6. 如何区分容器运行时挂载与攻击者路径遮蔽？

**简洁答案：** 看操作者、父子进程、挂载目标、镜像和容器生命周期、传播属性及后续执行链；容器创建期的一组成套挂载通常符合运行时基线，异常进程对宿主机敏感路径的局部替换则更值得调查。

**关键知识点：**

- 容器运行时、systemd、包管理器和部署工具都可能合法地执行挂载操作。
- 服务进程启动后突然加入其他 namespace，或非预期用户对敏感目录建立可写覆盖，是上下文风险，不是单字段定罪。
- 规则要考虑 Pod 重建、镜像升级、临时卷和 overlay 层变化，避免把每次部署都报成攻击。
- 告警应展示前后挂载差异、操作者、进程链和后续访问，而不是只显示一条 syscall 名称。

**Go 落地思路：**

- 基线按运行时、镜像/工作负载身份和路径范围分组，避免用全主机单一静态 mount 列表。
- 将挂载变化与 `exec`、敏感文件访问、权限变更和外联按 namespace 与短时间窗口关联。
- 提供可审计的窄范围例外，并记录命中的规则、被抑制原因和基线版本。

### 7. 挂载扫描和事件采集如何控制性能，并说明盲区？

**简洁答案：** 事件驱动优先，快照按风险定向执行；复用 `/proc` 读取和解析结果，限制并发与频率，并将快照延迟、失败和事件丢失作为采集健康度上报。

**关键知识点：**

- 每个事件都扫描全机所有进程的 mountinfo，会让高进程数主机产生大量重复 I/O。
- 只做周期快照可能漏掉两个周期之间创建又删除的挂载。
- procfs 权限受限、容器 PID namespace 隔离、Agent 重启或内核事件缓冲区丢失都形成可见性缺口。
- 不能把“扫描没发现异常”表达成“确认没有挂载变化”。

**Go 落地思路：**

- 按 namespace 与进程根视图去重并设置有界 worker 池；视图一致的短时间重复请求合并。缓存设置 TTL，重启或身份变化后重新采样，避免将 inode 或 mount ID 复用当作同一实体。
- 优先刷新收到挂载行为事件或承载高价值工作负载的 namespace，普通进程低频兜底。
- 导出队列丢失、procfs 读取错误、快照年龄和解析错误指标；高压时保证控制面和高危行为事件优先。

### 8. 只监控传统 `mount()`，为什么仍可能漏报？

**简洁答案：** Linux 还有通过文件描述符创建、克隆和附着挂载对象的接口。只监听传统 `mount()` 无法覆盖全部挂载变化；要按采集能力支持相关接口，并以视图快照验证最终状态。

**关键知识点：**

- `fsopen`、`fsconfig`、`fsmount` 可完成文件系统配置和分离挂载对象的创建，`move_mount` 可以将它附着到挂载点。
- `open_tree` 的克隆模式也可以产生分离的挂载树；创建对象不等于目标路径已经被覆盖。
- 路径参数可能依赖目录 fd，不能只复制字符串而忽略调用时的 fd 上下文。

**Go 落地思路：**

- 能力清单分别记录传统挂载调用、新挂载接口、namespace 切换与快照能力，避免一个 `mount_supported=true` 掩盖缺口。
- 按进程身份关联 fd 操作；无法解析源对象时保留原始参数并标记来源未知，用成功附着后的快照补证。
- 区分“尝试调用”“调用成功”和“视图已改变”，规则根据证据级别告警。

### 9. 为什么原来的 inotify watch 不能证明新视图仍受监控？

**简洁答案：** 在已监控目录上覆盖挂载，不会自动把原有 inotify watch 转移到新文件系统；挂载操作本身也不会产生对应的 inotify 通知。原 watch 还在，不代表新可见目录中的写入可见。

**关键知识点：**

- inotify 的覆盖挂载盲区属于监控对象变化，不能靠“watch 创建成功”这个历史状态判断当前覆盖率。
- 原目录可能没有被删除，新视图里的文件却来自另一个对象，因此看不到通知不一定是业务停止写入。
- fanotify 是否覆盖新挂载取决于 mark 类型、文件系统支持和权限，切换后端也要核对实际范围。

**Go 落地思路：**

- 发现敏感目录挂载变化后，将该视图的覆盖状态设为待核验，重新检查监控对象并按后端能力建立监听。
- 记录从视图变化到监听恢复之间的空窗；对新视图做有限快照只能补当前状态，不能声称补齐所有历史写入。
- 客户反馈“目录有变化但没告警”时，先比较 Agent 与业务进程的 namespace、根视图、挂载点和 watcher 绑定对象，再排查队列丢失。

## 学习要点

- 理解 `CLONE_NEWNS`、bind mount、mount propagation，以及 shared/slave/private 的事件传播差异。
- 能解释 `/proc/<pid>/mountinfo` 字段、八进制转义、root 与 mount point 的区别。
- 区分路径、文件实体、挂载点和 mount namespace 身份；不把 mount ID 当作永久对象 ID。
- 熟悉 Go 的 procfs 读取、进程生命周期校验、并发限流和采集降级设计。
- 能说明 audit/eBPF 实时事件与 mountinfo 周期快照各自的覆盖边界。

## 小练习 / 复盘题

1. 设计一个事件模型，能区分“进程换了 namespace”“敏感目录被覆盖”和“快照不可读”。列出身份字段、时间字段、来源字段和失败状态。
2. 容器启动时出现 `/etc/hosts`、`/etc/hostname` 和运行时目录挂载，服务运行数小时后某 Web 子进程又创建一个覆盖 `/etc/cron.d` 的挂载。你会收集哪些前后证据，如何排除合法操作？
3. 写出 mountinfo 单行解析的测试样例，覆盖 ` - ` 分隔符、传播可选字段和包含 `\040` 的挂载路径。
4. 如果 Agent 只能每分钟读取一次 mountinfo，攻击者在 10 秒内挂载、执行并卸载，哪些检测结论仍然成立？如何在告警中说明盲区？
