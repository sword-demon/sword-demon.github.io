# 制造业 PHP 面试题：UniApp、小程序与 APP（121—150）

车间移动端的重点是扫码操作、网络波动、重复提交、身份归属和错误恢复。本篇以工单查询、扫码报工、质量拍照和离线补传为主线。

::: info 平台边界
UniApp 提供跨端开发能力，但不代表所有平台 API、权限、存储和后台能力相同。以下回答需结合项目使用的 Vue 版本、运行端、原生插件及平台文档验证。
:::

## 一、页面与跨端开发

### 121. 为什么选择 UniApp？它有哪些限制？

**参考回答：** 可以复用 Vue 体系下的页面、业务状态和请求逻辑，覆盖小程序、APP 等目标端，降低多端维护成本。但渲染机制、组件支持、权限、原生能力和发布方式有差异，必须围绕实际目标端验证，而非承诺一份代码完全无差异运行。

**追问要点：** 先确认使用传统 UniApp 还是其他产品形态，以及 Vue、构建工具和端版本，不能混用不同文档中的能力。

### 122. UniApp 和普通 Vue Web 项目有什么不同？

**参考回答：** 业务响应式思路可以复用，但页面组件、路由、生命周期和平台 API 有额外约束。DOM、浏览器插件、Cookie 和 Web 存储的假设未必在小程序或原生端成立，应使用项目约定的跨端能力并保留必要的平台适配。

**追问要点：** 不能把依赖浏览器 DOM 的 UI 库直接当成跨端组件库；性能优化也要看目标平台实际渲染和通信成本。

### 123. `onLoad`、`onShow`、`onReady` 适合做什么？

**参考回答：** `onLoad` 通常处理页面初次加载参数与初始化，`onShow` 在页面显示时触发，适合按需检查返回后的数据变化，`onReady` 适合依赖首次渲染完成的操作。组件钩子和页面钩子应按所用版本及组件类型使用。

**追问要点：** 每次 `onShow` 都无条件请求所有接口，会导致重复加载；应结合失效标记和请求去重，离开页面后还要清理监听与定时器。

### 124. 工单列表、详情和报工页面之间怎样传数据？

**参考回答：** 路由传稳定标识，详情页面从接口读取权威数据；跨页面共享的身份和必要状态使用项目现有状态管理。不要把整份工单 JSON 或可篡改的权限结果放在 URL 中，并在提交前重新验证服务端状态。

**追问要点：** 返回列表可通过明确的刷新标记或既有事件机制更新，避免用多个全局变量维持不清晰的页面关系。

### 125. 列表加载更多、筛选和搜索如何避免数据错乱？

**参考回答：** 筛选条件改变时重置分页和数据，区分首次加载、刷新与追加的状态。为请求设置序号或取消旧请求，避免旧搜索结果覆盖新条件；追加时按业务 ID 去重，并根据后端分页契约判断是否还有数据。

**追问要点：** 游标应和当前筛选绑定，不能把 A 工厂最后一页的游标用于 B 工厂；请求失败后保留可恢复的界面和重试入口。

### 126. 请求封装应统一哪些内容？

**参考回答：** 统一服务地址、认证头、超时、请求 ID、响应解析和错误分类，页面仍决定具体业务交互。区分网络失败、HTTP 错误和业务冲突，不对所有 POST 自动重试，也不要每个失败同时弹出多个提示。

**追问要点：** `uni.request` 的成功回调说明收到响应，不代表 HTTP 状态或业务结果成功；还要检查状态码及明确的响应字段。

### 127. 微信小程序登录为什么不能把 `code` 当用户身份？

**参考回答:** 登录 `code` 是临时且只能使用一次的凭证, 应交给后端通过 `code2Session` 与微信服务交换身份信息, 再映射企业员工并签发业务登录凭证. `session_key` 由服务端保管, 不下发到客户端作为业务 Token. 微信身份不自动等于公司授权, 仍需处理员工绑定、账号停用、工厂和岗位权限. [U9][U9]

**追问要点：** AppSecret 和平台会话密钥不放到客户端；不能相信客户端直接传来的 `openid` 或员工 ID 就完成登录。

### 128. 多个请求同时遇到 Token 过期怎么办？

**参考回答：** 采用单次刷新协调：第一个请求执行刷新，其余等待同一结果；刷新成功后仅对允许安全重放的请求进行一次重放。刷新失败清理登录态并引导重新认证，防止刷新接口再次触发无限递归。

**追问要点：** 业务写入重放要复用原幂等键；不能把所有 401 都认为可刷新，停用账号和权限撤销可能需要立即终止会话。

### 129. 小程序和 APP 中的 Token 如何存储？

**参考回答：** 按平台能力和风险选择存储，控制凭证有效期及撤销能力，不在日志和错误上报中输出明文。普通持久化存储不是天然安全保险箱，APP 如需较高保障可使用经过验证的系统安全存储方案；客户端不保存用户登录密码。

**追问要点：** 服务端始终执行授权，共享终端换账号时清除或隔离缓存、草稿和附件，防止上一人的数据被下一人看到。

### 130. 扫码报工如何处理错误码和恶意输入？

**参考回答：** 按业务定义解析码类型、格式和长度，区分工单码、物料码和批次码，再到服务端校验有效性、归属及状态。扫码内容作为外部输入处理，不能扫描任意 URL 就自动跳转、下载或执行指令。

**追问要点：** 连续扫码要考虑相机回调重复、焦点与节流，但服务端仍需幂等。对过期、错工单和跨工厂的码给出具体可操作提示。

## 二、离线与同步

### 131. 报工页面怎样避免重复提交？

**参考回答：** 按一次业务操作生成稳定 `client_request_id`，提交时锁定交互并保存待处理状态；网络重试、页面重进和状态查询继续使用原键。服务端通过唯一约束和事务返回同一次操作结果，按钮防抖只减少误触。

**追问要点：** 用户想新建第二次报工才生成新键；编辑未提交草稿和更改已发送请求是不同动作，同键不同内容必须识别为冲突。

### 132. 离线功能能做到“和在线完全一样”吗？

**参考回答：** 不能。离线端无法可靠知道最新库存、权限、质量状态和工艺变更，应限制为允许离线采集的动作，保存草稿或待同步记录，最终由服务端确认。质量放行等高风险动作通常需要在线校验，具体按批准规则确定。

**追问要点：** 离线展示要区分“已本地保存”与“已服务端确认”，并显示缓存时间和待同步数量，避免现场人员误以为已入账。

### 133. 小程序和 APP 的离线数据都可以直接用 SQLite 吗？

**参考回答：** 不能这样假设。小程序通常使用平台提供的本地存储和文件能力，并受容量与生命周期限制；APP 可根据运行环境使用 SQLite 等原生能力，需核对 API、插件和真机支持。共享业务模型可复用，存储实现按平台选择。

**追问要点：** 小程序同步存储会阻塞当前执行，较多读写可评估异步 API。无论平台，都需验证写入失败、空间不足、数据升级和卸载清理行为。

### 134. 本地待同步队列最少需要哪些字段？

**参考回答：** 稳定请求 ID、所属账号和工厂、操作类型、payload 版本、内容、创建时间、同步状态、尝试次数及最后错误。对存在依赖的记录保留关联 ID，附件单独记录上传状态，不能只存一段 JSON 就不知道处理进度。

**追问要点：** 持久化成功后才提示本地已保存，读取恢复时先校验结构和版本。敏感信息按最小化原则保存，并定义本地保留和清理策略。

### 135. 待同步、处理中、成功、冲突应怎样流转？

**参考回答：** 待同步由同步器领取后转处理中；明确成功后记录服务端单号；网络或临时错误回到可重试状态；库存、工单版本等业务冲突进入待人工处理。APP 崩溃留下的处理中任务应通过超时恢复及服务端查询确认结果。

**追问要点：** 删除本地记录前确保已获得最终业务结果，并按需要保留回执；不能收到 HTTP 200 就立即清空全部待同步数据。

### 136. 手机显示有网络，为什么同步仍可能失败？

**参考回答：** 网络状态只说明部分连接条件，可能遇到内网未连通、认证门户、DNS、TLS、代理或服务不可达。同步以实际接口结果为准，使用合理超时、有限重试和清晰错误提示，网络恢复事件只是触发重试的信号。

**追问要点：** 不要每秒无限探测所有任务，也不要在网络切换时生成新业务键；控制并发和退避，避免恢复后集中压垮服务端。

### 137. 离线期间工单关闭或库存不足了，客户端怎么办？

**参考回答：** 服务端拒绝不再满足条件的动作并返回冲突类型、当前状态及可选处理方式；客户端展示原始待提交内容，让授权人员修改、转单、取消或走补录审批。不能自动覆盖新状态或强制扣成负库存。

**追问要点：** 原始采集时间保留，但不能把设备时间当成绕过工单关闭规则的依据。修改内容后使用契约允许的新操作或修订关系。

### 138. 换账号、Token 失效时，离线记录由谁提交？

**参考回答：** 本地记录绑定原操作者与组织，换账号不应悄悄用新账号提交旧记录。需要原用户重新认证后同步，或按授权的交接、复核流程处理，保留实际采集者、提交者和原因。界面应明确提示尚有待处理记录。

**追问要点：** 不能因为怕数据丢失就在退出时不受控地暴露旧账号草稿，也不能默认清空所有生产记录；按既定策略处理并明确结果。

### 139. APP 退到后台或小程序关闭后，还能保证继续同步吗？

**参考回答：** 不能承诺。操作系统与平台会限制或终止后台执行，应先持久化队列，在再次启动、回到前台或具备允许能力时恢复；真正需要持续采集的任务通常由稳定网关或服务器承担。

**追问要点：** 进程被杀、设备关机和应用升级后都应测试队列恢复；仅注册网络监听器不能保证关闭后的后台上传。

### 140. 本地创建记录和上传附件有依赖时，怎样安排？

**参考回答：** 使用稳定关联 ID 表达主记录与附件关系，按接口契约先取得上传标识或先创建草稿，全部必要附件完整后再提交确认。每一步可查询、可重试，服务端不能把缺附件的半成品误认为质量记录完成。

**追问要点：** 清理孤立附件前确认其未被有效记录引用；附件修改后应更新对应版本和摘要，不能继续绑定旧签署记录。

## 三、真机能力、性能与发布

### 141. 图片上传失败、文件过大和拍照权限被拒绝怎么处理？

**参考回答：** 拍照或选择文件前后处理平台权限与用户取消，校验类型和大小，按业务允许的清晰度压缩，并提供进度与可恢复失败状态。服务端重新校验，重要原始证据是否允许压缩需事先明确，不能默认丢弃原件。

**追问要点：** 前端限制不能代替服务端检查；分片上传要验证组装、摘要和权限，重复上传不应生成无法管理的大量附件。

### 142. 小程序接口在开发工具能用，真机失败怎么办？

**参考回答：** 检查合法请求域名、HTTPS 证书和完整链、平台限制、登录环境、网络路由及上传下载域名配置。开发工具跳过校验的设置不能证明正式版本可用，应记录真机错误并与服务端访问日志对应。

**追问要点：** `localhost` 指向设备自身，电脑可访问的内网地址手机未必可访问；开发、体验和正式版还可能使用不同配置。

### 143. 长列表、扫码页面卡顿应怎样优化？

**参考回答：** 先通过真机观察渲染、请求和内存，列表分页并减少不必要字段，使用稳定 key，避免频繁更新巨大响应式对象。扫码回调做适度节流，图片使用合适尺寸，离开页面清理监听和相机相关资源。

**追问要点：** 虚拟列表是否适配目标端要验证，不能只看浏览器表现；优化后记录首屏、滚动、连续扫码和低端机数据。

### 144. 条件编译和平台适配代码怎样组织？

**参考回答：** 把扫描、存储、权限等确有差异的操作放在清楚的边界，使用项目已有的平台适配和条件编译模式，页面复用业务流程。不要在每个组件里散落大量平台判断，也不为从未支持的平台设计框架。

**追问要点：** 编译通过不代表运行正确，各目标端至少验证登录、核心页面、权限拒绝和提交恢复；原生插件还需验证包配置与版本兼容。

### 145. 小程序与 APP 发布上线各要注意什么？

**参考回答：** 小程序关注 AppID、环境地址、合法域名、隐私权限、体验版与审核发布；APP 关注包标识、签名证书、权限说明、原生插件、分发和版本兼容。后端在旧客户端仍运行时保持约定兼容，并明确最低支持版本和升级策略。

**追问要点：** 发布前验证生产配置、账号与数据隔离、离线队列升级和回退路径。热更新不能绕过平台规则、原生能力限制及企业变更要求。

## 四、平台数据与进阶追问

资料核对日期: **2026-11-16**. 本节引用传统 uni-app 文档, 不将其与 uni-app x 的能力混用. 容量、权限和 API 支持以具体运行端、基础库及构建版本为准; 默认值不是项目验收指标.

| 可核查事实 | 对实现的影响 | 一手来源 |
| --- | --- | --- |
| 微信 `wx.setStorage` 默认单 key 上限 1MB, 总量上限 10MB | 这是键值缓存额度, 不能当作文件系统额度或 APP 通用上限 | [U1][U1] [U2][U2] |
| 微信异步 `wx.setStorage` 的 `encrypt` 参数自基础库 2.21.3 支持; 文档列出的加密后有效上限为单 key 0.7MB、总量 7.1MB | 不能假设 uni-app 各端透传同一参数, 也不能按未加密容量规划加密队列 | [U2][U2] |
| `uni.request` 文档的 `timeout` 默认值为 60000 ms | 适用端及最低版本有单独兼容表; 请求封装应明确设置符合业务的超时 | [U3][U3] |
| `uni.saveFile` 成功后移动临时文件, 原 `tempFilePath` 不再可用 | 队列必须保存返回的新路径; 微信端需注意原 `wx.saveFile` 已停止维护的提示 | [U4][U4] |

### 146. 把所有离线报工塞进一个 Storage key, 为什么很快失败?

**参考回答:** 同时存在单项限制、总额度、序列化开销和写入失败. 微信默认单 key 1MB、总量 10MB, 即使拆 key 也不能绕开总额度. 待同步队列应有账号隔离、容量监测和可靠的状态更新, 附件使用适合目标端的文件能力, 不把大图片 Base64 放进业务队列. 写入失败时不能提示“已保存”. [U1][U1] [U2][U2]

**追问要点:** `getStorageInfo` 的 `currentSize`、`limitSize` 以 KB 表示. 为索引、状态和失败恢复预留空间, 不能按原始 JSON 字符数精确承诺可存多少条. 平台允许用户删除或因空间问题清理缓存, 本地缓存不等于服务端备份; 只能清理已确认且符合保留规则的数据. [U1][U1] [U2][U2]

### 147. 离线照片的临时路径已经存入队列, 为什么重启后仍找不到图片?

**参考回答:** 保存路径字符串不等于持久化文件. 先按平台支持的文件 API 保存资源, 成功后把持久化路径、业务关联、大小和必要摘要写入队列. `uni.saveFile` 会移动临时文件, 因此不能继续用旧路径. 微信端按官方维护建议评估 FileSystemManager 的保存能力, H5、APP 和其他小程序各自验证. [U4][U4]

**场景追问:** 模拟文件已保存但队列未写入、队列存在但文件缺失、上传成功但回执未落地等中断点. 恢复时核对文件和服务端状态, 对孤立资源按规则清理; 质量附件只有在服务器完整接收、验证并关联后才能标记完成. `uploadFile` 回调还需检查 `statusCode` 和业务响应. [U8][U8]

### 148. 调用了 `abort()`, 为什么旧搜索结果或报工副作用仍可能出现?

**参考回答:** `RequestTask.abort()` 用于中断客户端请求, 不能撤销服务端已经提交的事务. 搜索界面除尝试取消旧请求, 还应在写入页面状态前比较请求序号、筛选条件和当前账号. 报工超时或取消后属于结果可能未知的状态, 应使用原业务键查询和重试, 不能直接创建新操作. [U3][U3]

**追问要点:** 文档说明, 希望直接拿到 RequestTask 时需至少传入 `success`、`fail`、`complete` 中一个回调; 未传这些回调时可能返回 Promise 包装. 请求封装应明确暴露取消能力, 不能把 Promise 当任务对象调用 `abort()`. 页面卸载和账号切换也要使迟到响应失效. [U3][U3]

### 149. 接口很快, 为什么工单列表仍然卡? 应测哪些阶段?

**参考回答:** 接口耗时只覆盖部分链路. 传统 uni-app 的 app-vue 和小程序存在逻辑层与视图层之间的通信成本, 还可能耗时于响应解析、大对象更新、节点创建、图片解码和布局. 应分别测请求、数据处理、首次可交互和连续滚动, 在目标端真机验证, 不能只优化 SQL. [U5][U5]

**追问要点:** 减少传给视图的无关字段, 将更新限定到需要变化的组件, 使用分页和适配该端的长列表方案. 记录设备、数据规模、冷启动或热启动等条件, 对比相同条件下的结果; 不把 H5 的优化结论直接当成小程序或原生渲染结论.

### 150. 配了 `subPackages`, 是不是所有页面启动都会更快?

**参考回答:** 分包改变资源组织及加载时机, 效果取决于主包依赖和实际访问路径. 小程序首次进入分包可能需要下载, 预加载又会消耗网络和资源. 将高频入口与必要依赖合理留在主包, 检查构建产物, 分别测首次启动、首次进分包和再次访问. APP 对分包的支持与作用需按对应模式核对, 不能套用小程序下载机制. [U6][U6]

**场景追问:** 验证弱网、下载失败、直接进入业务页面和旧客户端调用新后端. `preloadRule` 是预加载配置, 不是离线数据同步机制; 分包大小限制随平台而异, 以该平台现行文档与开发工具检查结果为准. [U6][U6]

## 五、用断网与换账号检验离线闭环

**教学场景：** 员工 A 离线采集一次报工并拍照，恢复网络后服务端已提交，但客户端没有收到响应，随后设备切换到员工 B。

1. **采集时：** 将稳定操作 ID、账号、工厂、内容版本及附件持久化路径可靠保存，成功后显示“已本地保存，待同步”。不能把临时照片路径当永久文件。
2. **发送时：** 保持原操作 ID 和原始业务内容，记录处理中状态；同一次逻辑操作的多次网络尝试可以分别保留请求 ID。
3. **结果未知时：** 使用原操作 ID 查询服务端结果或按幂等契约重试。请求取消、页面关闭和网络超时都不能证明服务端已回滚。
4. **换账号时：** 停止旧账号同步和迟到响应写入当前页面，隔离原账号记录。B 不应直接读取或以自己的身份提交 A 的草稿；后续由 A 重新认证或走受控交接。
5. **恢复时：** 服务端重新检查当前权限和业务状态；只有确认业务结果及必要附件完整后，才标记成功并按保留策略清理本地数据。

::: tip 特别解释：防抖、节流、互斥与幂等
**防抖（Debounce）**把连续触发合并为一次执行，常用于搜索；**节流（Throttle）**限制一段时间内的执行频率，常用于扫码回调；**互斥（Mutual Exclusion）**避免同时执行；**幂等（Idempotency）**保证同一次业务操作重试不多产生效果。按钮禁用只能减少误触，无法解决进程重启或服务端重复处理。
:::

**自测：** 分别在“保存照片后”“发出请求后”“服务端提交后”“回执保存前”终止应用并重启，再测试账号切换。检查记录可恢复、附件可定位、A 的数据不泄露给 B，且服务端只产生一次业务效果；真机结果应另行记录，不能由此场景描述推定通过。

## 关键术语与专业解释

| 术语 | 专业解释 | 易错边界 |
| --- | --- | --- |
| 页面生命周期 | 页面加载、显示、初次渲染完成和卸载等阶段的回调约定 | `onShow` 可多次触发, 不等于仅初始化一次. [U7][U7] |
| RequestTask | 一次网络请求对应的任务对象, 可提供取消等控制能力 | 与 Promise 的完成结果表达不同, 取消不等于服务端回滚. [U3][U3] |
| HTTP 状态 / 业务状态 | 前者来自响应协议, 后者由接口契约描述报工或单据结果 | 收到响应、HTTP 成功、业务已确认需分层判断. [U3][U3] [U8][U8] |
| Storage Quota | 平台对本地键值数据规定的容量配额 | 不是设备剩余磁盘空间, 也不是文件存储配额. [U1][U1] [U2][U2] |
| Temporary / Saved File | 临时资源与通过平台能力保存的本地文件 | 持久化路径仍有平台生命周期和清理规则, 不等于永久备份. [U4][U4] |
| 逻辑层 / 视图层 | 分别承载业务逻辑与界面渲染的运行部分 | 非 H5 端的数据跨层通信可能成为性能瓶颈. [U5][U5] |
| Subpackage / Preload | 将部分资源划入子包, 以及按规则提前加载相关资源 | 不能保证首次访问分包无网络等待. [U6][U6] |
| `code` / `openid` / `session_key` | 微信登录临时凭证、该小程序下的用户标识和会话密钥 | 不等同于企业员工授权或业务 Token, 会话密钥不下发客户端. [U9][U9] |
| Single-flight, 单次刷新协调 | 工程上让同一时段的重复刷新请求共享一个执行结果 | 本文的并发协调策略, 不是 `uni.request` 自动提供的保证; 失败也要结束等待. |
| 离线队列 / 冲突 | 前者保存待服务端确认的操作, 后者表示操作与当前权威状态不兼容 | 本文的业务状态模型, 不把本地成功当作库存或质量放行已确认. |

### 移动端关键词补充

| 关键词 | 通俗解释与本篇场景 | 易错边界 |
| --- | --- | --- |
| Token / Session | Token 是请求携带的凭证；Session 表示会话状态，具体存放位置依方案而定 | Token 不一定是 JWT，退出页面也不等于服务端凭证已撤销 |
| Access Token / Refresh Token | 前者访问受保护资源，后者在支持刷新机制的协议中换取新的访问凭证 | 不是每套登录都提供刷新令牌；刷新失败要结束等待与重试 |
| Promise / Callback | Promise 表达异步完成或失败；Callback 是由异步流程调用的函数 | 都不自动提供请求取消或服务端回滚能力 |
| Payload / Schema Version | Payload 是业务载荷；Schema Version 标识载荷的结构版本 | 应用升级后要能识别旧离线记录，不能盲目按新字段解释 |
| 乐观 UI（Optimistic UI） | 在服务端确认前先更新界面，提高反馈速度 | 扣料、放行等动作要明确“待确认”，失败需可恢复 |
| 冲突（Conflict） | 请求内容与当前工单、库存、版本或权限不兼容 | 与断网不同，原样无限重试通常不能解决 |
| TLS / HTTPS | TLS 保护传输通道；HTTPS 是通过 TLS 传输 HTTP | 证书有效不等于用户有权读取该工单 |
| 冷启动 / 热启动 | 通常分别指从未运行状态启动与从后台等已有运行状态恢复 | 测量需说明平台及具体状态，不能混用不同条件比较性能 |
