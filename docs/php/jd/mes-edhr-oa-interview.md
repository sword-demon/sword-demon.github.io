# 制造业 PHP 面试题：MES、E-DHR 与 OA（91—120）

本篇重点是将业务规则转成字段、状态、权限、校验与证据。E-DHR 指 Electronic Device History Record，可理解为电子器械历史记录；企业中也常围绕生产批次组织相关记录，其具体范围应由实际产品与质量流程定义。

::: warning 回答边界
这些是软件设计与面试准备建议。法规适用范围、记录保存期限、签名方式和验证要求，应由企业质量及法规人员结合产品、市场和预期用途确认，不能用“做了日志”直接推出系统合规。
:::

## 一、生产与质量链路

### 91. 如何讲清从工单到入库的一条完整生产链路？

**参考回答：** 从工单及版本释放开始，关联工艺路线、物料批次和设备，执行各工序并报工，记录物料消耗和生产参数，完成检验、偏差处理与审核放行，再形成入库及 ERP 同步。每个节点明确触发条件、责任角色、业务编号和异常出口。

**追问要点：** 不是所有企业都按固定顺序运行，部分检验可穿插在工序中；应以实际工艺和质量规则确定哪些条件必须阻断后续动作。

### 92. 工单和工序状态机应该怎样设计？

**参考回答：** 将状态和允许动作列成转换表，注明角色、前置条件和副作用。例如工单从草稿到已释放、执行中、暂停、完成、关闭；工序有独立进度，不能用一个工单状态代替所有工序事实。每次转换做并发校验并留审计。

**追问要点：** 取消执行中的工单通常涉及已消耗物料、在制品和 ERP 状态，不能直接把状态改回草稿，必须定义退料、结算或冲销规则。

### 93. 工艺路线、BOM 和检验标准变更后，历史记录怎么办？

**参考回答：** 使用受控版本，工单释放时绑定适用版本或快照，历史记录继续引用当时生效的规则。新版本的审批、生效时间和适用范围明确记录；在制品是否切换由业务和质量评估后通过受控变更执行。

**追问要点：** 不应直接更新主数据后让历史报工展示新标准，否则无法重建“当时为什么判定合格”。

### 94. 报工接口应该校验哪些业务条件？

**参考回答：** 校验操作者及工厂权限、工单和工序状态、设备或工位绑定、前序条件、批次有效性、数量精度、良品与报废关系、物料与质量约束，并防止重复。动态条件在事务内核对，超量或补录按明确权限和审批规则处理。

**追问要点：** 必须确认报工数量是本次增量还是累计值，两种语义混用会重复累计；返工数量也不能直接加到首次产出中。

### 95. 批次拆分与合并如何实现追溯？

**参考回答：** 建立输入批次到输出批次的关系记录，保留操作、数量、单位、损耗和原因。拆分形成一个父批次到多个子批次，合并可能多个输入到一个输出，不能仅用一个 `parent_id` 覆盖全部关系。

**追问要点：** 防止关系循环，验证数量平衡和允许混批条件；合并后仍要能反查每个供应商批次及受影响成品。

### 96. 领料、耗料、退料、补料有什么区别？

**参考回答：** 领料描述物料转移或发放，耗料描述实际生产消耗，退料描述未消耗物料退回，补料是追加投入；它们的库存地点、可用量和成本含义可能不同。应采用带来源单据的业务流水，而不是只改库存最终值。

**追问要点：** BOM 理论消耗和实际消耗可能不同，自动倒扣的触发时点、损耗率、替代料和差异审批要由业务明确。

### 97. 返工、返修和报废为什么不能直接修改原报工数量？

**参考回答：** 原报工是已经发生的生产事实，直接覆盖会破坏历史与对账。返工或返修应关联原批次和原因，定义新工序、检验及产出规则；报废形成受控记录和对应库存动作。合法更正也应保留原值、原因、操作人和版本。

**追问要点：** 返工后合格不代表首次合格，应区分最终合格率和一次通过率，避免指标失真。

### 98. 质量检验模块最重要的建模点是什么？

**参考回答：** 区分检验任务、样本、检验项目、原始结果、规则版本和最终判定，保存单位、精度、上下限、设备及操作者。判定规则考虑边界值、缺失值、无效测量和复测，不以一个“合格”布尔字段代替所有依据。

**追问要点：** 抽样方法和接受准则应引用已批准的质量规则，开发不自行创造；复测不能静默覆盖首次失败结果。

### 99. 有一项检验不合格，系统应该如何阻断？

**参考回答：** 根据规则冻结相关批次、工序或后续放行，产生不合格或偏差处理记录，由有权限人员评审处置。重检、返工、报废或特定批准要有明确路径，并与入库和对外同步保持一致。

**追问要点：** 不能仅在页面按钮上限制，API、批量导入、后台任务都必须执行相同规则；管理员身份不应默认跳过质量门禁。

### 100. 入库和质量放行是否是同一个动作？

**参考回答：** 不一定。实物可进入待检或隔离库位，但未必允许成为可领用、可销售库存；质量放行、实物入库和财务过账通常是不同维度。应明确可用库存的条件和每一步的系统责任。

**追问要点：** 若 ERP 入库成功而 MES 状态更新失败，应按来源单据查询并修复一致性，避免重新创建第二张入库单。

### 101. 召回追溯功能怎样验证有效？

**参考回答：** 从一个原材料批次正向找到消耗、在制品、成品批次及发运，从成品反向找到来源物料、工序、设备、人员、参数和质量记录。覆盖拆分、合并、替代、返工和历史归档，验证完整性和查询耗时。

**追问要点：** 结果应展示来源、数量及关系依据，并验证跨工厂权限；不能用当前 BOM 推算历史真实投料关系。

## 二、电子记录、权限与审计

### 102. 一份 E-DHR 应怎样组织，才能支持复核？

**参考回答：** 以器械或生产批次为入口，聚合适用版本、生产与物料记录、检验结果、偏差处置、签名与放行，并能定位每项记录的原始依据。采用清单明确必需内容及缺失项，复核看到的是受控版本和关联事实。

**追问要点：** 仅导出一份 PDF 不等于完成电子记录管理，还要维护可检索、可归属、修订追踪和保留能力。

### 103. ALCOA+ 如何落成开发要求？

**参考回答:** 按 MHRA 数据完整性指南, ALCOA 指可归属、清晰可读、同步记录、原始和准确, “+” 强调完整、一致、持久及可用. “同步记录”指在活动发生时记录, 不是不同数据库已经同步的意思. 开发上体现为独立账号、来源设备标识、原始数据保存、事件与录入时间、版本字段、输入与换算校验、审计、备份和授权检索. 具体适用要求仍由产品、市场及质量体系确定. [E7][E7]

**追问要点：** ALCOA+ 可作为数据完整性检查框架，但不是一个加字段就能自动获得的认证；人员流程和系统运行控制同样重要。

### 104. 审计追踪与普通应用日志有什么区别？

**参考回答：** 应用日志主要服务排障，审计追踪服务重建关键记录的创建、修改、审核或作废过程。审计需包含对象与版本、操作者、动作、时间、原因及必要前后值，访问和保留也应受控。

**追问要点：** 请求日志不一定包含业务最终结果；异步写审计可能丢失关键证据。必须一起成立的业务变更与关键审计应同事务保存。

### 105. 使用 Eloquent Observer 就能完整记录所有审计吗？

**参考回答：** 不能。批量更新、原生 SQL、其他程序写库等路径可能不触发模型事件，而且事件未必知道业务原因、签名和状态语义。应让关键业务动作走明确的受控服务入口，在事务中写审计，并识别其他合法写入路径。

**追问要点：** 数据库触发器也缺少完整业务身份上下文，不能简单替代应用审计；需要按实际架构组合控制并验证覆盖。

### 106. 如何降低管理员篡改审计记录的风险？

**参考回答：** 普通业务身份不允许更新或删除审计，应用、运维与数据库管理权限分离，关键记录可异地归集并按要求使用不可变存储、备份和访问告警。定期复核特权操作，并验证恢复和完整性检查流程。

**关键边界：** 数据库超级用户通常仍具有很强能力，不能承诺单张表绝对不可篡改。哈希链能帮助发现改变，但若全部材料由同一人控制，也不能独立证明未被重建。

### 107. 电子签名与点击“审核通过”有什么区别？

**参考回答：** 电子签名需要可信确认签署身份、签署意图，并与具体记录及其版本绑定，显示签署人、时间和含义，防止被复制到其他记录。具体认证和签名措施按适用要求确定，不能只在审核表填当前用户名。

**追问要点：** 敏感认证凭证不写日志；签名失败不改变业务状态。技术上的数字签名可以是实现手段，但不能直接等同于完整的电子签名管理要求。

### 108. 已经审核签名的批记录发现填错了，应该怎样修改？

**参考回答：** 通过受控更正、补充记录或新版本表达变更，保留原记录、错误原因、申请人和复核。评估原签名、放行及外部系统是否受到影响，新的审核绑定更正后的版本，而不是静默继承原签名。

**追问要点：** 不使用直接改库绕过流程；紧急处理也要有授权、证据、影响评估和后续复核。

### 109. 权限模型如何支持工厂、车间和双人复核？

**参考回答：** 功能权限表达能做什么，数据范围表达能操作哪里，字段权限控制可见与可改项；关键动作再按当前对象状态和人员资格授权。双人复核需要检查创建人与复核人是否不同，不能只看两个按钮是否被点击。

**追问要点：** 共享账号无法可靠归属个人；临时授权需有期限、理由和审批，人员离职或岗位变化后要回收权限并处理待办。

### 110. 记录时间、导出和长期保留应如何设计？

**参考回答：** 使用明确时区策略，区分事件发生、接收、操作和签署时间，保留原始来源时间与偏差信息。导出包含标识、版本、单位、时间含义和必要审计关联；按批准期限保留数据及读取能力，并验证备份恢复与检索。

**追问要点：** 不能任意补写为当前时间掩盖迟录，也不能把通用天数当作所有医疗器械记录的法定保留期限。

## 三、OA 与可配置业务流程

### 111. 一个基本 OA 审批流程需要哪些对象？

**参考回答：** 流程定义及版本描述规则，流程实例描述一次申请，节点任务描述当前处理工作，动作记录描述同意、拒绝、转交等事实。申请表单与业务单据保持关联，不能只在业务表塞一个 `approver_id`。

**追问要点：** 简单固定流程可按现有模式直接实现，只有明确需要频繁配置时才引入流程引擎；流程定义更改不应自动覆盖已运行实例。

### 112. 串行审批、会签和或签怎样实现？

**参考回答：** 串行按节点顺序推进；会签按规则要求全部或一定比例通过；或签允许符合条件的任意一人完成。需要在并发事务中判断节点是否已结束，避免两人同时通过时重复生成下游任务。

**追问要点：** 明确拒绝优先级、弃权、超时和剩余待办处理，节点完结后旧任务操作应返回状态冲突并保留尝试信息。

### 113. 撤回、驳回、转交、加签和代理应怎样处理？

**参考回答：** 每个动作有独立前置条件和权限，明确是否撤销后续任务、回到哪个节点、是否重审以及谁承担责任。代理需有授权范围和期限，记录实际操作人及被代理人；不能简单把当前审批人字段改成另一个人。

**追问要点：** 已触发 ERP 过账或质量放行的流程，撤回可能需要业务冲销，不能仅撤回 OA 记录。

### 114. 可配置字段和插件定制怎样避免越做越复杂？

**参考回答：** 先明确现有字段、规则和扩展点，只开放有业务价值的配置，例如字段类型、必填、可见范围与批准的计算规则。配置要版本化、校验、测试和受控发布，插件复用统一的权限、事务和审计入口。

**追问要点：** 不允许配置直接执行任意 PHP、SQL 或不受控表达式。插件失败应明确回滚或降级策略，不能绕过关键质量校验。

### 115. 面试官让你现场设计一个“批次放行”功能，如何回答？

**参考回答：** 先列放行条件：生产记录完整、检验合格、偏差关闭、签署人员有资格且版本一致；再设计状态与权限、记录和审计、并发控制以及对 ERP 的可靠通知。实施上在事务内锁定批次并核对相关受控状态，写放行事实、签名关联和 outbox。

**追问要点：** 其他修改路径也必须遵守同一锁定或版本协议，单独锁住批次不必然阻止检验子记录被并发修改。测试需覆盖签名失败、并发放行、重复请求及同步超时。

## 四、法规时点与进阶追问

资料核对日期: **2026-11-16**. 本节引用美国 FDA 规则和相关一手资料说明设计边界, 不将其自动套用于所有中国工厂或全部产品. 法规适用性由质量及法规人员确认; 表中的日期和标准来自官方资料, 计算示例为教学假设, 不是实际工厂业绩.

| 可核查事实 | 对原有回答的补充 | 一手来源 |
| --- | --- | --- |
| QMSR 已于 2026-02-02 生效, 在 21 CFR Part 820 中纳入 ISO 13485:2016 | 不能仍把 QMSR 写成未来要求, 也不能只引用旧版 820.184 作为当前完整依据 | [E1][E1] |
| QMSR 最终规则不再单列旧 QSR 的 DHR、DMR、DHF 等记录类型术语 | 术语调整不等于取消生产、设计和质量记录要求; 企业可继续使用 E-DHR 作为系统业务名称 | [E2][E2], Comment 31 与 Response |
| FDA 2026 年 2 月发布的 CSA 最终指南替代 2025-09-24 版本 | 软件保证需围绕预期用途和风险取证, 不是取消软件验证或测试 | [E3][E3] |
| NIST 将 OEE 表述为可用率、性能率与质量率的乘积 | 高最终良率不能替代设备效率, 返工是否计入首次合格必须明确 | [E4][E4] |

### 116. QMSR 生效后, E-DHR 功能和旧 DHR 记录是否应该删除或改名?

**参考回答:** 不应仅因法规术语变化就删除记录或强制改名. FDA 的最终规则说明, 原记录要素主要纳入 ISO 13485 的文档和生产要求, 例如器械或批次记录. 软件应先建立旧记录、当前适用要求和字段证据的映射, 保留历史版本与检索能力, 由质量部门评估差距, 而非机械替换页面标题. [E1][E1] [E2][E2]

**追问要点:** 区分法规生效日期、企业程序生效日期和工单采用的规则版本. 新要求不能成为无痕重写旧生产记录的理由; 本文不声称取得 ISO 证书就自动满足全部 FDA 要求.

### 117. 所有 OA 审批都必须套用 21 CFR Part 11 吗?

**参考回答:** 先判断记录是否属于适用的 FDA 基础法规要求、是否采用电子形式履行记录或签名义务, 再确认 Part 11 的范围和适用控制. 普通行政审批与用于质量放行的电子记录不能仅因都叫“审批”就采用同一合规结论. FDA 的 Scope and Application 指南解释适用范围及执法裁量, 后者不等于可以不遵守基础法规. [E5][E5]

**场景追问:** 对适用的签署记录, 将签署人姓名、签署时间和签署含义与具体记录版本关联, 并在可读副本中体现; 评估记录链接是否可被割离或复制. 对照 11.50、11.70, 不把一张签名图片或用户名字段当成完整电子签名控制. [E6][E6]

### 118. “采用 CSA, 不需要测试脚本和证据了”正确吗?

**参考回答:** 不正确. CSA 是围绕生产或质量管理软件的预期用途及风险建立可信度的方法. FDA 指南允许按风险选择适当的保证活动, 其中可包括脚本化和非脚本化测试, 但仍需要足以说明活动、发现的问题、结论和责任的记录. 页面配色和错误放行批次的功能不应采用相同的风险判断. [E3][E3]

**追问要点:** 对“检验不合格不得放行”, 至少定义失败后果、控制措施、越权和并发场景、实际结果及缺陷关闭证据. 是否采用探索式测试不是免除证据的理由, 指南建议也不能表述成所有项目必须采用的唯一测试模板.

### 119. OEE 三个分项都达到 90%, 综合效率就是 90% 吗?

**参考回答:** 不是. OEE 按分项相乘而不是取平均. 教学示例中, 若可用率、性能率、质量率各为 90%, 则 `OEE = 0.90 × 0.90 × 0.90 = 72.9%`. 该数字是公式计算结果, 不是行业调查或企业实测. 必须固定计划生产时间、理想节拍和首次合格的统计口径. [E4][E4]

**场景追问:** 假设投入 100 件, 首次通过 92 件, 另 8 件返工后全部合格. 首次通过率为 92%, 最终合格比例可以为 100%, 二者不可替换. 不把某个常见 OEE 百分比当成所有产品、节拍和工艺通用的验收线; 无产出或无计划生产时间时按规则显示不可计算, 不能伪造 100%.

### 120. 把检验 CSV 导入 E-DHR, 行数一致就算迁移成功了吗?

**参考回答:** 还要验证内容、身份、时间、单位、规则版本和记录关联. 可按数据完整性框架核对原始值及元数据是否保留, 转换过程是否可重现, 缺失和异常是否完整列出, 目标记录是否可读可查. MHRA 的 ALCOA 及完整、一致、持久、可用属性可帮助形成检查表, 但不能直接推出该文件对本企业具有法律适用性. [E7][E7]

**追问要点:** 教学测试包含同值重复行、空值、负数、时区、精度变化及附件缺失. 文件摘要可检查文件是否改变, 不能单独证明来源真实或业务内容正确; 旧签名和审计不应伪装成迁移当天的新签署.

## 五、从一张批次记录理解质量门禁

**教学场景：** 批次 B 的检验记录版本为 v3，复核人正在签署；另一名操作员同时提交检验更正，准备生成 v4。

**设计重点：** 签署对象必须包含记录标识及版本。更正和放行路径采用共同的并发控制协议：如果 v4 先提交，基于 v3 的放行应报告版本冲突并要求重新复核；如果 v3 先完成签署，后续更正应生成可追溯修订，并评估原放行是否需暂停或重新批准，不能静默覆盖已签内容。

| 必须保留的信息 | 用途 |
| --- | --- |
| 原始结果、单位、设备、事件时间 | 回答当时测得什么、由谁或什么设备产生 |
| 适用标准及版本、判定依据 | 回答当时为什么判定为合格或不合格 |
| 更正前后值、原因、实际操作人 | 重建更正过程，避免只看到最终值 |
| 签署人、时间、含义、记录版本 | 明确签的是哪份内容以及承担什么动作责任 |
| 放行状态、下游通知及确认 | 防止本地撤销后 ERP 仍按旧状态继续使用 |

::: tip 特别解释：追溯、审计与签名
**追溯（Traceability）**连接物料、工序、批次和去向；**审计追踪（Audit Trail）**重建谁在何时改变了哪条记录及原因；**电子签名（Electronic Signature）**表达可归属的签署意图并绑定记录。三者相互配合，不能用一条“审核通过”日志全部替代。
:::

**自测：** 同时提交更正与放行、重复点击签署、使用创建人自审、读取历史 v3。验收应能证明不存在“签名显示 v3、实际展示内容已被换成 v4”的混淆，并能还原各动作的事实与顺序。实际签署及放行规则仍以企业确认的流程为准。

## 关键术语与专业解释

| 术语 | 专业解释 | 面试边界 |
| --- | --- | --- |
| MES | Manufacturing Execution System, 制造执行系统, 围绕生产执行组织工作流、进度、过程数据及异常提示 | FDA 指南用这些功能举例, 但实际风险取决于是否直接控制关键生产参数, 不能仅凭系统名称判断. [E3][E3] |
| ERP | Enterprise Resource Planning, 企业资源计划系统, 用于协调物料、订单、库存等企业资源与业务流程 | FDA 指南中的物料补给案例说明同类功能因人工复核等控制不同而风险不同; 与 MES 的职责按项目契约划分. [E3][E3] |
| OA | Office Automation, 办公自动化; 本文用它指行政协作、表单和审批等业务能力 | 属于通用业务用语, 不是统一的法规系统分类; 接入质量放行后仍需单独评估记录与签名控制. |
| BOM | Bill of Materials, 物料清单, 描述生产产品所需的组件及其计划消耗等信息 | 与描述工序及资源的工艺路线相互配合, 不能把计划用量当作实际耗料; 版本和适用条件需受控. [E8][E8] |
| QMS / QMSR | QMS 是质量管理体系; QMSR 是 FDA 当前 Part 820 的质量管理体系法规 | 管理体系不等于一套软件, 适用范围需单独确认. [E1][E1] |
| E-DHR / DHR | Electronic Device History Record / Device History Record, 用于组织器械或批次生产历史的业务记录概念 | 当前法规术语与旧 QSR 不完全相同, 历史要素不能因更名消失. [E2][E2] |
| DMR / DHF | 旧 QSR 中的 Device Master Record 与 Design History File, 分别围绕制造规范和设计开发历史 | 不能把设计规范、生产执行事实和设计验证证据混在同一份“批记录”中. [E2][E2] |
| Predicate Rules | 在 Part 11 语境中规定记录或签名义务的基础法规 | 先确定记录义务, 再分析电子形式的控制要求. [E5][E5] |
| Audit Trail | 支持重建电子记录创建、修改或删除等过程的受控追踪记录 | 不等于可随意覆盖的调试日志. [E6][E6], 11.10(e) |
| Electronic Signature | 由个人执行、采纳或授权, 用作与手写签名等效的电子符号或数据组合 | 与密码学数字签名相关但不等同, 需要身份、含义和记录绑定控制. [E6][E6] |
| ALCOA+ | 可归属、可读、同时记录、原始、准确, 加完整、一致、持久、可用 | 是数据完整性检查框架, 不是认证证书. [E7][E7] |
| CSA | Computer Software Assurance, 用适当活动建立对软件预期用途的信心 | 风险导向不等于免测试或免记录. [E3][E3] |
| OEE / FPY | Overall Equipment Effectiveness 是设备综合效率; First Pass Yield 是首次通过率 | 返工后合格不能回填成首次通过, OEE 还包括时间和速度维度. [E4][E4] |

### 制造业务关键词补充

| 关键词 | 通俗解释与本篇场景 | 业务边界 |
| --- | --- | --- |
| 工单 / 工序 / 工艺路线 | 工单规定生产任务；工序是加工或检验步骤；工艺路线规定步骤及其关系 | 工单完成不自动证明每项质量条件满足 |
| 报工 / WIP（Work in Process，在制品） | 报工记录一次执行事实；在制品处于尚未完成全部生产流程的阶段 | 报工数量需明确增量或累计；在制品不能直接当成可销售成品 |
| 批次 / 序列号（Serial Number） | 批次关联一组具有共同追溯属性的对象；序列号标识单个对象 | 批次追溯与单件追溯的关系粒度不同 |
| 倒扣料（Backflush） | 按报工等触发事件及已配置规则自动计算、登记物料消耗 | 理论量需与实际耗用核对；超耗、替代料和返工不能自动忽略 |
| 状态机 / 门禁（Guard） | 状态机规定可达状态和转换；门禁规定转换时必须满足的条件 | 后端各入口都要校验，不能只控制按钮 |
| 版本 / 快照 | 版本标识某次受控修订；快照保存某时点所用内容 | 只存版本号但允许内容被覆盖，仍不能还原历史 |
| 偏差 / 不合格 | 偏差表示偏离已批准要求或过程；不合格表示未满足某项要求 | 分类、调查和处置规则由质量流程定义，开发不能自动放行 |
| CAPA | Corrective and Preventive Action，纠正和预防措施 | 不只是修正一条数据，还要按适用流程分析原因、实施措施并验证效果 |
| SoD（Segregation of Duties，职责分离） | 将关键操作与复核等职责适当分离 | 两个角色名不证明是两个人，需核对实际身份和授权 |
