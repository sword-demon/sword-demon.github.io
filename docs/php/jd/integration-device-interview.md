# 制造业 PHP 面试题：系统集成与设备联网（61—90）

集成面试的重点是解释数据从哪里来、以谁为准、怎样防重、失败怎样恢复。本篇沿着工单下发、报工回传、质量记录与入库同步展开。

## 一、接口契约与安全

### 61. ERP、MES、OA、E-DHR 分别负责什么？

**参考回答：** ERP 通常负责资源计划、采购与财务相关业务，MES 负责车间执行，OA 承载行政或审批流程，E-DHR 汇集与器械生产历史相关的受控电子记录。实际职责存在产品和企业差异，应先画业务边界，确定每类主数据和状态由谁维护。

**追问要点：** 不能让四个系统都随意修改同一工单状态；要定义权威来源、允许回写的字段、事件触发点和冲突处理人。

### 62. 新对接一家 ERP，第一步做什么？

**参考回答：** 先对齐业务对象和时序，再确认接口。至少形成系统职责、字段映射、编码规则、状态转换、数量单位、唯一键、鉴权、错误码、超时、重试、对账和验收清单。确定测试环境及双方联系人，使用同一组样例串通完整链路。

**追问要点：** 不要只拿到 URL 就开发；需先确认“接口接收成功”是否代表“业务单据已过账”，以及如何查询最终结果。

### 63. 主数据编码不一致时怎样处理？

**参考回答：** 明确物料、产品、工厂、仓库和单位的权威来源，维护带来源系统及有效期的映射。未知编码不能默默转换成默认值，应进入待处理状态；映射变更需评估已发生业务记录是否仍使用原版本。

**场景追问：** 同一物料编码在不同工厂含义不同，映射键必须包含工厂范围。名称可变化，不能拿名称作为长期关联键。

### 64. 一份可联调的接口文档要包含哪些内容？

**参考回答：** 除路径、方法和字段外，还应写明身份权限、数据范围、必填与可空、时间格式、单位精度、版本、幂等键、分页方式、错误码、状态含义和示例。异步接口还要给出结果查询、回调鉴权、超时和重放规则。

**追问要点：** 加入重复、冲突、部分失败和已处理的示例；文档和测试契约一起维护，避免代码已改而供应商仍按旧版调用。

### 65. 接口幂等键应该怎样设计？

**参考回答：** 用稳定标识表达同一个业务动作，例如来源系统、单据号、行号与动作版本；同一动作重试必须复用同一个键。键的范围应能区分冲销和重新确认等合法新动作，不能仅用工单号阻止该工单所有后续报工。

**追问要点：** 同键不同内容应冲突，摘要计算要采用约定的规范化方式。幂等记录保留时间要覆盖可能的补传和人工重放窗口。

### 66. 接口身份认证和数据签名有什么区别？

**参考回答：** 认证确认调用方身份，授权限制其可操作的业务范围，签名验证约定内容未被篡改且来自持有密钥的一方。可按双方能力采用服务凭证、OAuth2、HMAC 等方案，传输仍应使用 TLS。凭证应独立分配、按最小权限配置并支持轮换。

**追问要点：** HMAC 是共享密钥校验，不能直接等同于具有独立身份和记录绑定要求的电子签名；密钥也不能下发给普通小程序客户端。

### 67. 如何防止签名接口被重放？

**参考回答：** 签名覆盖约定的方法、路径、时间戳、nonce 和请求体摘要；校验签名后，在有效窗口内原子记录调用方与 nonce，拒绝重复使用。时间窗口要考虑允许的时钟偏差，但不能靠时间戳单独防重。

**追问要点：** URL 编码、JSON 序列化、字段顺序和原始 body 的签名规则必须一致；签名比较使用安全比较函数，并且业务层继续做幂等。

### 68. HTTP 状态码和业务错误码应该怎样分工？

**参考回答：** HTTP 表达请求层面的结果，例如未认证、禁止访问、输入不合法、资源冲突和服务不可用；业务码表达“物料未放行”“工单已关闭”等具体原因。成功响应还要区分已接收与已完成，避免客户端只看 200 就认定已扣料或入库。

**追问要点：** `202 Accepted` 表示接受异步处理，应返回任务标识与查询方式；不能把所有错误都返回 200 再让调用方猜测。

## 二、可靠同步与异常闭环

### 69. 外部接口超时，是否可以直接重试？

**参考回答：** 超时只能说明未在期限内拿到结果，不能证明对方未处理。查询类请求通常可按限额重试，写入类请求需先具备稳定幂等键和结果查询能力，再按契约查询或重发；无法确认的状态进入待核对，而非创建新的业务流水。

**场景追问：** ERP 已生成入库单但响应丢失，重试必须引用原来源单号，否则会造成重复入库。

### 70. 哪些错误应该重试，哪些不应该？

**参考回答：** 网络故障、部分临时服务错误、限流可按接口契约采用有上限的指数退避与抖动，限流还应尊重 `Retry-After`。字段缺失、编码错误和业务规则拒绝通常需要修正数据，不能机械重试。状态未知则先查询确认。

**追问要点：** 认证失败应检查配置或按受控流程刷新凭证，不能每条任务都无限刷新。设置最大次数、最大时长、并发上限和人工处理入口。

### 71. 为什么生产关键链路常采用 Outbox？

**参考回答：** 它解决本地业务提交与发送事件不能原子完成的问题。在报工事务中同时写待发送事件，后台提交后扫描发送，记录尝试和结果；这样业务成功后即使进程崩溃，也能继续找到未发送事件。

**关键边界：** 远端成功后、本地标记前仍可能崩溃，因此 outbox 通常提供至少一次发送，消费者仍必须幂等。扫描器还需安全领取任务、处理超时占用并监控积压。

### 72. 消息队列能保证 Exactly Once 吗？

**参考回答：** 不能把中间件某个范围的语义直接扩展为跨 MySQL、HTTP 和 ERP 的业务保证。工程上常按至少一次投递设计，通过业务唯一键、事务和消费记录让重复执行不产生重复效果，再用对账发现遗漏。

**追问要点：** ACK 丢失和消费者崩溃会触发重投；外部副作用与本地消费标记之间仍存在一致性窗口，必须逐个边界分析。

### 73. 工单事件乱序到达怎么办？

**参考回答：** 每个业务对象携带来源版本或序号，拒绝覆盖较新状态，必要时等待缺失前序、查询来源快照或进入异常队列。消息分区可改善同一工单内的顺序，但不能取代消费者对版本和状态转换的检查。

**追问要点：** 时间戳存在时钟偏差和同一时刻多事件问题，不宜作为唯一顺序依据。版本是否连续、是否允许跳过，要由事件契约说明。

### 74. 一次批量同步中部分明细失败，怎么设计返回和重试？

**参考回答：** 先确定业务要求整单原子还是逐行独立，返回每行稳定标识、状态、错误码及可否重试。若逐行处理，成功行无需重复执行，失败行按原幂等键补传；整单要求则应拒绝部分入账，或由明确的业务补偿流程恢复。

**追问要点：** HTTP 请求整体成功不代表每一行成功，必须记录批次与明细结果，避免按返回条数推断已成功的具体记录。

### 75. 对方只有同步 HTTP 接口，没有幂等能力怎么办？

**参考回答：** 先争取让对方按来源单号唯一或提供业务结果查询；本地串行和锁只能减少并发重复，无法消除远端成功、响应丢失的窗口。无法改造时将不确定结果隔离、停止自动重发，并通过查询报表或人工核对确认后继续。

**追问要点：** 应明确这项能力限制和业务处理责任，不能承诺“加一个 Redis 锁就绝不重复”。

### 76. 对账应该比对什么，而不只是总数量？

**参考回答：** 按来源单号和明细行比较存在性、数量、单位、批次、状态、版本及必要的业务金额。划定时间水位，给正常同步延迟留窗口，区分缺失、重复、冲突和状态未知，产出可执行的问题清单。

**追问要点：** 总量相同可能掩盖两条明细互相抵消。对账发现差异后先确认权威来源，再通过受控补传或冲销修复，不能直接覆盖两边数据。

### 77. 死信和人工补偿怎样做到可控？

**参考回答：** 保存失败事件、业务键、脱敏摘要、尝试次数、最后错误和下次动作。操作台支持查询、复核和按原键重放，修改 payload 应产生新版本并保留原因；关键冲销需要授权审批。

**追问要点：** 重放前检查远端是否已成功，重放后重新对账。补偿本身也可能失败，必须有状态、审计和明确责任人。

### 78. 如何监控一条完整的生产数据交互链路？

**参考回答：** 为一次请求生成关联 ID，异步事件再保留事件 ID、来源单号和因果关系。监控成功率、业务拒绝率、处理耗时、积压年龄、重试次数、死信及对账差异，告警应能定位到业务对象和处理入口。

**追问要点：** “HTTP 全部 200”不能证明业务健康；长时间没有事件可能意味着采集停了，应监控预期流量、心跳和最后成功时间。

## 三、设备联网与数据采集

### 79. PHP 是否适合直接连接所有 PLC 采集数据？

**参考回答：** 通常应区分设备采集层和业务接收层。PLC、串口或工业协议由适配的采集程序或网关处理，Laravel 接收标准化事件，完成设备身份、业务关联、校验、存储和追溯。已有合适采集组件应优先复用。

**追问要点：** 高频实时控制、设备安全联锁不能依赖普通 Web 请求或不稳定公网；业务系统也不能在未明确授权与验证时向设备发送控制命令。

### 80. Modbus、OPC UA、MQTT 有什么区别？

**参考回答:** Modbus 常面向寄存器等数据读取, 需约定地址、类型、字节序和缩放; 例如 V1.1b3 的 `0x03` 读保持寄存器一次最多读取 125 个寄存器. OPC UA 提供较丰富的信息模型及安全能力, 其 DataValue 可携带值、状态码和时间戳; MQTT 是发布订阅消息协议, 需要另外定义主题、payload 和业务语义. 实际由设备能力、网络与安全要求共同决定, 不能把协议支持等同于安全配置已经正确启用. [I1][I1] [I2][I2] [I3][I3]

**追问要点：** 能订阅到 MQTT 消息不代表知道它属于哪个工单；协议连通与业务数据正确是两个验收层次。

### 81. 设备采集记录最少应保留哪些信息？

**参考回答：** 设备身份、点位或参数、原始值、转换值、单位、质量标志、事件时间、接收时间、来源序号、网关和协议映射版本。与工单、工序、批次的绑定应有明确依据，无法确定时先保留未关联状态。

**追问要点：** 不要根据“这台设备当前工单”直接给迟到数据绑定新批次，应按采集时刻的有效绑定或记录携带的生产标识匹配。

### 82. 设备断线后补传，如何防重与识别数据缺口？

**参考回答：** 网关使用持久化缓冲，事件带设备、启动会话和递增序号或稳定事件 ID；服务端唯一约束防重，通过序号缺口及心跳识别异常。设备重启可能清零序号，不能只用设备 ID 加序号长期唯一。

**追问要点：** 补传区分采集时间与接收时间，监控缓冲容量和最老事件年龄；断电前未持久化的样本可能永久丢失，必须说明实际保证范围。

### 83. 设备时间不准、数值越界或单位错误怎样处理？

**参考回答：** 保留原始数据和质量标志，将时钟偏差、协议无效值、业务越界分别判断；明确单位与缩放版本，异常数据进入隔离或待复核。不能无记录地“修正”原值，也不能把通讯失败填成测量值零。

**追问要点：** 自动判定是否放行必须使用经确认的有效数据和规则版本。时钟同步解决时间偏差，但不能证明传感器已校准或测量有效。

### 84. MQTT QoS 2 是否意味着生产系统绝不会重复扣料？

**参考回答：** 不是。QoS 约束的是协议参与方之间的消息交付过程，不能覆盖应用写库、网关重启后重放或调用 ERP 的完整副作用。业务仍要有事件唯一标识和事务幂等，不能在每次收到参数消息时直接无条件扣料。

**追问要点：** 保留消息可能在订阅后重新送达旧状态，离线会话也影响补发；需要明确主题区分“最新状态”和“不可重复的业务事件”。

### 85. 设备供应商说“数据没问题”，你怎样组织联调？

**参考回答：** 选一个已知工单和标准样本，从设备原始读数、网关解析、消息内容、接收日志到数据库逐层核对；固定点位映射、单位、采样频率和时间，记录双方版本及预期。覆盖断网、重启、重复、乱序、异常值和恢复补传。

**追问要点：** 用同一个事件 ID 或来源序号关联证据，把问题定位到具体边界；形成责任人、修复期限、复测和最终关闭记录。

## 四、协议数据与进阶追问

资料核对日期: **2026-11-16**. 以下区分协议规范、厂商实现与工程建议. 标准上限不是设备吞吐承诺, 示例数字不是项目实测结果.

| 可核查事实 | 实际含义 | 一手来源 |
| --- | --- | --- |
| Modbus V1.1b3 的功能码 `0x03` 一次读取 1-125 个连续保持寄存器, 每个寄存器 16 bit | 这是该功能的协议范围, 实际设备可有更严格限制 | [I1][I1], 第 6.3 节 |
| MQTT 5.0 中 CONNECT 未携带 Session Expiry Interval 时默认值为 0 | 默认不能据此承诺断线后保留会话; 还需核对服务端协商结果 | [I2][I2], 第 3.1.2.11.2 节 |
| OPC UA DataValue 包含值、StatusCode 和来源/服务端时间戳等信息 | 收到数字不等于测量有效, 也不等于刚刚采集 | [I3][I3], 第 7.11 节 |
| HTTP `Retry-After` 可为 HTTP 日期或非负整数秒数 | 不能一律当毫秒解析; 429 是否携带该字段由服务端决定 | [I4][I4], 第 10.2.3 节; [I5][I5], 第 4 节 |

### 86. 设备手册写寄存器 40001, 为什么程序读出来是错的?

**参考回答:** 先核对手册的引用编号与报文地址. Modbus PDU 从 0 开始寻址, 手册的 40001 等表示法不能不经确认就直接作为报文地址. 再核对功能码、寄存器数量、有符号性、比例因子及跨寄存器字序. 标准规定寄存器内高字节在前, 不应由此推断所有厂商的 32 位浮点布局都相同. [I1][I1]

**场景追问:** 用已知样本比较原始十六进制数据与工程量, 固化点位表版本. 例如读取 200 个连续保持寄存器时, 至少需要按 `0x03` 的上限拆分, 还要遵守设备更小的限制; 分两次读取不自动形成同一采样时刻的原子快照.

### 87. MQTT 开了 QoS 1, 为什么断线重连后仍可能没有历史消息?

**参考回答:** QoS 是交付等级, 不替代会话与存储策略. MQTT 5.0 还需核对 ClientID、Clean Start、Session Expiry Interval、CONNACK 的 Session Present, 以及消息过期与 broker 限额. 会话过期后, 不能只靠原订阅恢复完整历史. Retained Message 保存主题的保留状态, 不是全部事件档案, 也不属于会话状态. [I2][I2]

**追问要点:** 将断网、客户端重启、broker 重启分别演练. 业务事件另外使用持久化缓冲、稳定事件 ID 和缺口对账; 状态主题与扣料指令分开, 不把订阅时收到的旧保留消息当成新操作.

### 88. OPC UA 返回一个正常范围的数值, 可以直接用于质量判定吗?

**参考回答:** 先检查 DataValue 的 StatusCode, 再核对来源时间、单位、工单绑定和采集有效性. 规范要求错误状态下忽略 value; SourceTimestamp 必须使用 UTC, 应表示值或状态最后变化的时间, 转发时保留原值. 它不一定每次扫描都更新, 因此不能仅凭时间较早就判定设备离线, 还需结合服务端时间、采样配置和心跳判断. 数字正常也可能伴随坏质量或无法确认的数据新鲜度. [I3][I3] [I6][I6]

**场景追问:** 给相同数值分别配置 Good、Uncertain、Bad 和过期时间, 验证页面提示与放行门禁. 对缺失时间戳保留缺失状态, 网关接收时间单独记录, 不伪造为设备测量时间.

### 89. ERP 返回 429 或 503, 怎么既遵守限流又不重复入库?

**参考回答:** 429 表示请求过多, 503 表示暂时不可用; 按契约解析 `Retry-After`, 缺失时采用有上限的退避与抖动. 这些状态码不能代替业务结果查询, 写入仍复用原幂等键, 超出总重试预算后转待核对. HTTP 幂等描述重复请求的预期效果, 不要求每次响应内容完全相同. [I4][I4] [I5][I5]

**追问要点:** 设计客户端、网关与 worker 的统一重试预算. 不因限流创建新入库单号, 不因响应含有日期就忽略时钟偏差, 也不让每一层自行无限重试.

### 90. 为什么每一层只重试几次, 也会把故障放大?

**参考回答:** 重试会增加已过载依赖的工作量. AWS 的工程文章举例: 5 层调用各最多尝试 3 次, 最深依赖可能承受 `3^5 = 243` 次调用. 这里的 3 是包含首次在内的尝试次数, 不是额外重试 3 次. 这一推演不是吞吐基准, 用来说明应在明确的一层控制重试, 配合超时、退避、抖动和幂等. [I7][I7]

**场景追问:** 网关离线补传应有限速、优先级和有界缓冲, 以消费能力决定发送速度. 缓冲即将满时发出告警并按批准策略处理, 不静默丢弃质量记录, 不单纯扩大 worker 数量压垮 ERP.

## 五、把“ERP 超时”拆成可恢复状态

**教学场景：** MES 已提交本地报工和 Outbox，worker 发起 ERP 入库后超时。此时唯一确定的是“没有收到可用回执”，不能据此判断 ERP 没有入库。

| 观察到的事实 | 本地状态与下一步 | 为什么这样处理 |
| --- | --- | --- |
| 收到明确成功回执，业务单号匹配 | 保存远端单号和确认信息 | HTTP 成功之外，还要核对业务成功及单据对应关系 |
| 超时，但按来源单号查询到已入库 | 补记成功并核对数量、单位、明细 | 查询恢复结果，避免生成新单 |
| 查询暂时未找到，但远端有延迟可见性 | 保持结果未知，按契约继续查询 | 暂时查不到不构成“从未处理”的证据 |
| 远端支持稳定来源键幂等 | 在有限预算内使用原键重试 | 重发同一次操作，不新建一笔业务 |
| 远端既无查询也无幂等能力 | 转人工核查，保留请求与结果证据 | 本地锁无法证明远端是否已产生副作用 |

::: tip 特别解释：幂等键、请求 ID、追踪 ID
**幂等键**标识同一次业务操作，重试时保持稳定；**请求 ID**标识一次调用尝试，多次重试可以不同；**追踪 ID（Trace ID）**串联一次分布式调用过程。三者应建立关联，但不能直接用每次变化的请求 ID 去重业务。
:::

**自测：** 在模拟服务中设置“远端已入库、响应被丢弃”，检查系统能否恢复远端单号且最终只有一笔入库。再模拟重复回调和迟到失败回调，确认已确认成功的结果不会被较旧消息覆盖；后续真实冲销应作为独立业务事件处理。

## 关键术语与专业解释

| 术语 | 专业解释 | 易错边界 |
| --- | --- | --- |
| PDU | Protocol Data Unit, 协议数据单元; Modbus PDU 由功能码及功能数据构成 | 与包含传输相关头尾的 ADU 不同. [I1][I1] |
| Holding Register | Modbus 数据模型中的 16 位保持寄存器 | 工程单位、缩放和多寄存器拼接需设备约定. [I1][I1] |
| QoS 0 / 1 / 2 | MQTT 的至多一次、至少一次、恰好一次交付等级 | 不自动扩展成跨数据库和 ERP 的业务原子性. [I2][I2] |
| Session Expiry / Message Expiry | 前者约束会话状态保留, 后者约束消息有效期 | 会话还在不代表每条消息永不过期. [I2][I2] |
| Retained Message | broker 按主题保存的保留消息, 可按订阅规则提供给订阅者 | 不是事件历史库. [I2][I2] |
| StatusCode / SourceTimestamp | OPC UA 的值状态及来源时间语义 | 不能只取数值丢掉质量和时间信息. [I3][I3] [I6][I6] |
| Idempotency, 幂等 | 相同请求重复执行的预期效果与执行一次相同 | 不是所有调用只能返回一次响应, 也不是 POST 自动具备的保证. [I4][I4], 第 9.2.2 节 |
| Backoff / Jitter | 退避增加再次尝试前的等待, 抖动分散客户端同时重试 | 两者不替代总尝试预算与业务幂等. [I7][I7] |
| Outbox, 事务发件箱 | 本地事务同时保存业务变更和待发事件, 由独立发送过程转交下游 | 架构模式而非 MQTT 功能; 仍须处理重复发送. [I8][I8] |

### 对接与设备关键词补充

| 关键词 | 通俗解释与本篇场景 | 必须明确的边界 |
| --- | --- | --- |
| 接口契约（Contract） | 双方约定字段、单位、身份、错误码、幂等、超时和版本行为 | JSON 格式一致不代表业务语义一致 |
| 主数据 / 权威来源 | 主数据是物料、组织等共享基础信息；权威来源是某类事实最终以谁为准 | 不一定由同一个系统负责所有字段 |
| 最终一致性 | 允许短暂差异，通过可靠传播和恢复机制在约定条件下收敛 | 需要明确延迟目标、失败出口和对账，不能只说“等一会儿就好” |
| 补偿 / 回滚 | 补偿用新的业务动作纠正已发生效果；事务回滚撤销尚未提交的本地修改 | 已入库后冲销不是把原记录删除 |
| DLQ（Dead-Letter Queue，死信队列） | 接收无法正常处理的消息，供定位和受控重放 | 消息进入死信不代表业务已经恢复 |
| HMAC / Nonce | HMAC 用共享密钥验证消息完整性与来源；Nonce 是协议中用于区分请求的新鲜值 | HMAC 不加密内容；Nonce 要配合服务端校验和防重放记录 |
| PLC / SCADA / 网关 | PLC 执行现场控制，SCADA 负责监控与数据采集，网关负责协议接入和转发等边缘处理 | PHP 业务接口不应被当作确定性实时控制回路 |
| 点位 / 采样 / 上报 | 点位标识一个测量或状态；采样是读取；上报是传输 | 采样频率与上报频率可能不同，批量上报需保留各样本时间 |
| 字节序 / 字序 / 缩放 | 字节序决定字节排列，字序决定多寄存器排列，缩放将原始值换为工程量 | 读到两个合法寄存器，不代表组合出的温度就正确 |
