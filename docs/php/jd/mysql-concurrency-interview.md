# 制造业 PHP 面试题：MySQL、并发与报表（31—60）

本篇围绕生产报工、批次库存和统计报表展开。回答 SQL 问题时，应把查询模式、约束、并发风险和验证方式一起说明。

::: info 版本边界
以下主要讨论 MySQL InnoDB。执行计划、在线 DDL、检查约束和索引优化能力随版本不同；例如 `EXPLAIN ANALYZE` 需要 MySQL 8.0.18 及以上，并会实际执行查询。
:::

## 一、建模与索引

### 31. 工单、批次和报工应该放在一张表吗？

**参考回答：** 不应把不同粒度的数据混在一行。工单描述生产任务，批次描述可追溯的物料或产品集合，报工描述某次工序执行事实，消耗明细描述投入批次和数量。按实体分表并用明确关系关联，必要的汇总字段作为派生数据维护。

**追问要点：** 同一报工可能消耗多个物料批次，一张表反复增加“物料 1、物料 2”字段会破坏扩展性。批次拆分合并还需要独立的关系表。

### 32. 自增 ID、业务单号和幂等键分别有什么作用？

**参考回答：** 自增 ID 适合内部关联，业务单号用于人员沟通和跨系统对账，幂等键标识同一次业务请求。三者可以不同；业务单号不必含有所有业务含义，幂等键也不能每次重试重新生成。

**追问要点：** 唯一性范围要明确，例如 `(source_system, source_no)`，或包含工厂维度。禁止用 `MAX(id) + 1` 或当前秒数直接生成并发业务流水号。

### 33. 为什么数量、金额和测量值不能随便用 `FLOAT`？

**参考回答：** 二进制浮点数不能精确表示所有十进制小数，累计扣料或金额计算容易产生误差。固定精度数据通常用 `DECIMAL`，整数计件可用整数；测量原始值还应保留单位、仪器精度和原始表示。精度与舍入规则由业务确定。

**追问要点：** PHP 中也不能把所有 `DECIMAL` 字符串强转成 float 计算，可按范围使用最小单位整数或项目已有的十进制计算能力，并明确单位换算和舍入位置。

### 34. 联合索引如何按实际查询设计？

**参考回答：** 先列高频过滤、关联、排序和分页条件，再结合数据分布设计。例如按工厂、状态、时间和主键查询工单，可评估 `(factory_id, status, created_at, id)`，随后用执行计划和实际耗时验证，不能仅靠“区分度最高放前面”决定。

**追问要点：** 如果查询不按状态过滤，时间排序可能需要另一种索引。一个很长的联合索引无法覆盖所有访问模式，还会增加写入和存储成本。

### 35. “联合索引遇到范围查询，后面的列全部失效”正确吗？

**参考回答：** 这种说法过于绝对。范围条件通常限制后续列继续缩小连续索引扫描区间的能力，但后续列仍可能用于索引条件下推、覆盖查询或部分排序处理。实际使用情况还取决于谓词形式、优化器和版本。

**追问要点：** 同样不能说缺少最左列就绝不扫描该索引；可能发生全索引扫描或满足条件的跳跃扫描。应区分“使用索引”与“有效缩小扫描量”。

### 36. 覆盖索引和回表是什么？

**参考回答：** InnoDB 的二级索引记录包含主键，通过主键到聚簇索引取其他列是常说的回表。查询所需列已能从索引取得时，可减少回表。例如工单列表只返回编号、时间和状态，往往比 `SELECT *` 更容易优化。

**追问要点：** 不能为了覆盖一个低频查询把大文本放进索引。覆盖索引也不意味着扫描行数一定少，应继续检查过滤选择性。

### 37. `EXPLAIN` 应重点看哪些信息？

**参考回答：** 看表的访问顺序、访问方式、实际选择的索引、估算扫描行数、过滤比例、临时表和排序，再结合 SQL 业务语义判断。`rows` 是估算值，实际统计应通过可用的分析工具和运行指标验证。

**追问要点:** `Using index` 与 `Using index condition` 含义不同, `Using filesort` 也不等于一定使用磁盘排序. MySQL 从 8.0.18 引入 `EXPLAIN ANALYZE`, 它会实际执行所分析的语句并报告执行信息, 不是只读取估算计划; 生产使用前必须评估负载和执行成本. [M3][M3]

### 38. 为什么生产日报突然变慢？你会按什么顺序排查？

**参考回答：** 先确认数据量、查询条件、时间段和最近变更，再拆分接口耗时为 SQL、锁等待、数据传输、PHP 组装和导出。检查慢查询、执行计划、索引统计和是否出现 N+1，随后验证优化是否降低实际扫描量及整体耗时。

**场景追问：** 不要一开始就加缓存。若报表出现明细关联倍增，缓存只会更快地返回错误结果。

### 39. 深分页应该怎样优化？

**参考回答：** `OFFSET` 越大通常越需要扫描并丢弃前面的行。连续翻页或导出可使用基于稳定排序键的游标分页，例如按 `(created_at, id)` 共同排序，并记录上一页末尾两项值。排序键应能消除相同时间造成的不确定顺序。

**追问要点：** 游标分页不天然支持任意跳到第几页；后台若确实需要随机跳页，可保留有边界的页码方案。历史数据的并发变化还需结合快照要求处理。

## 二、事务与并发控制

### 40. ACID 在报工业务里分别体现为什么？

**参考回答：** 原子性保证报工和扣料一起提交或回滚；一致性依赖约束与业务规则共同维护；隔离性控制并发操作相互影响；持久性确保成功提交的数据按数据库配置可靠保存。事务不会自动知道“已冻结批次不许扣料”这类业务规则。

**追问要点：** 数据库原子提交不代表 ERP 同步也成功；持久性还受刷盘、存储和复制配置影响，备份与恢复是另一层保障。

### 41. RC 和 RR 有什么区别？

**参考回答：** InnoDB 的普通一致性读取在 RC 下通常每条语句建立新读视图，RR 下通常复用事务内首次一致性读建立的视图。锁定读取和更新读取当前可操作的数据，不能把所有 SQL 都理解成同一份快照。

**追问要点：** RR 不自动消除所有业务并发问题。先查询库存再无条件更新，仍可能丢失更新；需要条件更新、锁或版本号配合业务规则。

### 42. 两人同时扣减同一批物料，怎样避免负库存？

**参考回答：** 简单单行扣减可使用带条件的原子更新，例如 `UPDATE stocks SET available_qty = available_qty - :qty WHERE id = :id AND available_qty >= :qty`，检查影响行数。多物料与流水写入放入事务，并统一加锁顺序，任何一项不足都回滚。

**追问要点：** `qty` 必须是校验后的正数，并校验组织、批次放行状态和单位。单纯先 `SELECT` 再 `UPDATE`，或只在前端限制数量，无法处理并发。

### 43. `SELECT ... FOR UPDATE` 有哪些使用条件？

**参考回答：** 在明确的事务内查询并锁定后续要修改的数据，使用合适索引缩小扫描和锁定范围，事务尽快结束。先锁定再读取用于决策的最新状态，不能在锁外检查库存、锁内直接相信旧值。

**追问要点：** 锁范围与索引、查询条件和隔离级别有关，不保证任何 SQL 都“只锁一行”。事务里不要调用慢速 ERP 接口或等待用户确认。

### 44. 乐观锁与悲观锁如何选择？

**参考回答：** 低冲突的编辑页面可用版本号条件更新，版本不符提示用户重新查看；库存竞争或多个关联校验可评估悲观锁。乐观锁只检测冲突，不会自动合并两个不同的业务意图。

**场景追问：** 工艺规则编辑使用 `WHERE id = ? AND version = ?`，更新成功才递增版本并写审计；用户冲突后不能用旧表单无限重试覆盖新规则。

### 45. 行锁、间隙锁和临键锁怎么理解？

**参考回答：** 记录锁锁住索引记录，间隙锁限制向索引间隙插入，临键锁结合记录与前方间隙。InnoDB 在 RR 下部分范围锁定读取会使用这类锁控制并发插入，实际行为由查询方式和索引决定。

**追问要点：** 唯一索引的精确命中和非唯一范围扫描可能具有不同锁范围；RC 下的间隙锁行为也不同，不能只凭隔离级别名称推断所有场景。

### 46. 死锁如何诊断和处理？

**参考回答：** 保存死锁报告和事务 SQL，定位资源获取顺序、索引缺失和事务持续时间。通过固定更新顺序、缩小事务、补适合的索引减少死锁，对数据库已回滚的事务进行有限次数整体重试，并确保业务幂等。

**追问要点：** 死锁不等于数据库故障；锁等待超时与死锁的回滚范围可能不同，应用应按实际配置明确回滚整个业务事务，不可在异常后继续提交部分修改。

### 47. 幂等为什么一定要考虑数据库唯一约束？

**参考回答：** 并发请求可以同时通过“先查不存在”的判断，唯一约束提供最终的冲突仲裁。幂等记录与业务动作应建立原子关系，记录业务键、规范化请求摘要、状态和结果；重复请求返回原结果，同键不同内容返回冲突。

**追问要点：** 只在唯一键报错后返回“成功”不够，还要确认原请求已经成功、内容一致且当前用户有权读取该结果。不要把其他唯一约束错误误判为幂等命中。

### 48. 读写分离后，提交成功却查不到数据怎么处理？

**参考回答：** 先判断是否为复制延迟。关键的写后读、库存和放行校验应路由到主库，或使用有明确一致性保证的读取策略；非关键列表可接受并展示短暂延迟。Laravel 的粘性读取设置需按连接配置和实际生命周期验证。

**追问要点：** 当前请求内的粘性读取不等于下一次请求、队列任务也一定读主库。主从延迟还应监控，并明确报表的数据更新时间。

## 三、报表、变更与长期数据

### 49. 工单统计关联报工、消耗和检验表后，数量为什么翻倍？

**参考回答：** 多个一对多关系直接连接，会形成明细组合乘积，导致重复累加。应先按工单或目标粒度分别汇总各明细，再关联汇总结果，或按用途拆成独立查询。不要随意用 `SUM(DISTINCT qty)` 掩盖问题，相同数值可能对应不同真实记录。

**追问要点：** 用同一工单两次报工、三次消耗的样例验证，既检查汇总值，也检查没有任何明细时的零值语义。

### 50. 跨夜班次的日报按哪一天统计？

**参考回答：** 先由业务明确班次日历、时区、开始结束时间和归属日，再将统计窗口转换成明确时间范围。常用左闭右开区间，例如本日班次开始到下一班次开始之前，避免毫秒精度和边界重复计入。

**追问要点：** 设备事件时间、服务端接收时间可能不同，迟到补传如何重算必须约定。查询时间列时尽量使用范围过滤，避免无必要地对列套日期函数。

### 51. 良率、达成率和 OEE 有什么区别？

**参考回答：** 良率通常衡量合格产出与对应总产出的比例，达成率衡量实际完成与计划目标的关系，OEE 通常由可用率、性能率和质量率相乘得到。每项指标都要明确分子、分母、统计粒度和返工、报废、停机的处理规则。

**追问要点：** 汇总多个车间不能直接平均百分比，应按正确分母重新汇总。缺少可靠的运行时间、标准节拍和质量数据时，不应声称已准确算出 OEE。

### 52. 大数据量报表如何兼顾速度与正确性？

**参考回答：** 先优化查询和统计粒度，再按业务时效要求选择预聚合或异步生成。派生报表应记录统计口径、数据水位和生成时间，对迟到、冲销与修订数据提供重算机制；高风险放行判断不能使用可能过期的统计缓存。

**追问要点：** 导出使用明确的快照或截止水位；仅记录最大 ID 不能阻止旧记录被更新，需要结合数据不可变规则或快照策略定义一致性。

### 53. 给大表加字段、索引时怎样避免影响生产？

**参考回答：** 先确认 MySQL 版本、表大小、执行算法、磁盘余量与锁影响，在接近真实规模的环境演练。在线 DDL 也可能等待元数据锁，并增加 IO 或复制延迟；上线前设监控、窗口、停止条件和回退方案。

**追问要点：** 应用可用“先兼容新旧结构、再迁移数据、最后收紧约束”的方式发布。不得把“支持在线 DDL”理解为完全无阻塞、无风险。

### 54. 生产记录为什么不能简单软删除或直接归档？

**参考回答：** 软删除改变默认查询可见性，可能让批次追溯、对账或报表遗漏历史。关键记录应使用明确的作废、冲销和版本规则，保留原始关联及原因；归档需要保持可检索、可恢复和权限控制，并遵守已确认的保留要求。

**追问要点：** 唯一键与软删除的组合要实际验证。MySQL 唯一索引允许多个 `NULL`，因此 `(business_no, deleted_at)` 不一定能阻止多条未删除的重复单号。

### 55. 如何验证备份真正有用？

**参考回答：** 在隔离环境执行恢复演练，验证完整备份、所需日志和恢复步骤能达到约定 RPO、RTO。检查业务记录数量、关键约束、附件、审计和外部系统的对账情况，记录实际恢复耗时与丢失范围。

**追问要点：** 主从复制会复制误删，不能代替备份；数据库回到过去不意味着 ERP 也回滚，恢复后应按业务键做差异识别和受控补偿。

## 四、官方数据与进阶追问

资料核对日期: **2026-11-16**. 行为以 MySQL 8.4 InnoDB 文档为基线, 涉及功能引入版本时引用 8.0 手册. 不把这些结论直接套用到 MariaDB 或云数据库的兼容实现.

| 可核查事实 | 应用边界 | 官方来源 |
| --- | --- | --- |
| InnoDB 默认隔离级别为 `REPEATABLE READ` | 实际会话可能被连接配置覆盖, 应检查会话值 | [M1][M1] |
| `CHECK` 从 MySQL 8.0.16 起支持实际执行约束; 更早版本解析但忽略相应语法 | 不能因建表语句出现 `CHECK` 就认定数据已受保护 | [M2][M2] |
| `EXPLAIN ANALYZE` 从 8.0.18 起提供, 会实际执行语句 | 测试环境先验证成本, 不当作只读元数据查询随意执行 | [M3][M3] |
| MySQL 8.4 的 `innodb_lock_wait_timeout` 默认是 50 秒 | 这是 InnoDB 行锁等待参数, 不是 HTTP 超时或所有数据库锁的统一超时 | [M4][M4] |

### 56. 加了 `CHECK (available_qty >= 0)`, 为什么还不能保证库存正确?

**参考回答:** 先确认版本、约束是否 `ENFORCED`, 以及字段是否允许 `NULL`. `CHECK` 对表达式为 `TRUE` 或 `UNKNOWN` 的行放行, 所以非空数量还需 `NOT NULL`. 它可以拦截单行负数, 但不替代带条件扣减、跨行库存平衡、权限和库存流水事务. [M2][M2]

**场景追问:** 在隔离测试库尝试负数、零、`NULL` 和并发扣减, 检查错误及最终流水. 新增约束前先排查存量脏数据, 不靠上线时失败来发现历史问题.

### 57. 多个 Outbox worker 怎样领取任务? `SKIP LOCKED` 能用于库存盘点吗?

**参考回答:** 队列式表可在短事务中用 `FOR UPDATE SKIP LOCKED` 选择可领取行, 更新领取人、租约和状态后提交, 再执行外部调用. 它会跳过已被行锁锁住的记录, 不保证返回完整视图, 因而不适合作为库存余额或放行依据. `NOWAIT` 则在无法获得相应行锁时立即报错. [M5][M5]

**追问要点:** 领取查询要有合适索引; 空结果不代表所有任务已完成. 租约到期后的恢复、旧 worker 的迟到回写和远端业务幂等需另外设计. 官方同时提示这两种选项对 statement-based replication 不安全, 上线前核查复制模式. [M5][M5]

### 58. 一笔事务第二条 SQL 锁等待超时, 第一条会自动回滚吗?

**参考回答:** 默认情况下, 锁等待超时回滚当前语句, 不必然回滚之前已执行的整笔事务; `innodb_rollback_on_timeout` 会影响行为. 检测到死锁时, InnoDB 则回滚选中的整个受害事务. 对报工、扣料等原子业务, 应让异常退出事务并显式确认整体回滚, 再按幂等条件有限重试, 不吞异常继续提交. [M6][M6]

**场景追问:** 两个独立连接中, A 锁定库存行, B 先写报工再尝试扣料, 验证 B 超时后报工未被误提交. 数据库 50 秒默认值不是接口应等待 50 秒的理由, 应结合请求预算和业务容错设置. [M4][M4]

### 59. 一次只读长报表, 为什么也可能拖累写入和结构变更?

**参考回答:** 长时间持有一致性读视图可能阻碍旧版本的 purge, 增加 undo 保留和历史版本处理成本. 访问表的未结束事务还可能持有元数据锁, 导致 DDL 等待; 在线 DDL 也不能绕开全部元数据锁. 应检查事务年龄、历史列表和锁等待链, 而不是只看报表有没有 `UPDATE`. [M7][M7] [M8][M8]

**追问要点:** 分批提交可以缩短事务, 但会改变一致性快照语义. 应先约定报表截止水位及历史修订规则, 再选择只读副本、快照或预聚合, 不用“分页了”掩盖跨页口径变化.

### 60. `COMMIT` 已成功, 就能承诺断电和主库切换都不丢记录吗?

**参考回答:** 不能脱离配置和故障模型承诺. `innodb_flush_log_at_trx_commit` 控制 InnoDB redo 的提交刷盘策略, `sync_binlog` 控制 binlog 同步. 官方为事务复制场景的较强持久性建议两者设为 1, 仍要求操作系统和存储真实兑现落盘语义. 本地持久性不等于副本已确认或切换后零丢失. [M9][M9]

**追问要点:** 用批准的恢复演练验证备份、日志连续性、故障切换和业务对账. 不为提高压测成绩擅自弱化刷盘设置, 也不把双 1 等同于备份或端到端 RPO 为零.

## 五、用库存算例检验并发设计

**教学场景：** 某批次可用库存为 5 件，两次不同的合法操作各申请扣减 3 件。假设本例只有一个库存维度，不涉及预占、冻结或单位换算。

**错误推演：** 两个请求都先读到 5，各自判断足够，再把库存写为 2。如果两笔消耗流水都成功，账面只减少 3 件，却记录消耗 6 件。这是**丢失更新**的一种表现，库存没有负数也不代表正确。

**正确边界：** 在事务内执行包含工厂、批次和 `available_qty >= 本次数量` 的原子条件扣减，并检查受影响行数；或者使用一致的行锁协议后再校验。请求数量必须先验证为正数，库存记录的唯一性、可用状态和权限也必须成立。扣减、消耗流水与报工一起提交，失败时一起回滚。

| 验证输入 | 必须观察的业务结果 |
| --- | --- |
| 不同请求键并发扣减 3 件、3 件 | 仅一笔成功；库存为 2；已提交消耗合计为 3 |
| 同一请求键并发重试扣减 3 件 | 只有一份业务效果；重试可获得原结果，不能形成两条消耗 |
| 扣减后、写流水前发生异常 | 整个本地事务回滚；库存回到 5；没有已提交的消耗流水 |
| 提交成功后响应丢失 | 按原键查到已提交结果；重试不再扣减 |

::: tip 特别解释：不变量比“接口返回成功”更重要
**不变量（Invariant）**是无论执行顺序如何都必须成立的规则。本例应满足“期初库存 5 − 已提交消耗 = 当前库存”，并且同一业务操作最多生效一次。实际系统还要把入库、退料、调整、冻结与预占按业务口径纳入核对，不能直接照搬这个简化等式。
:::

## 关键术语与专业解释

| 术语 | 专业解释 | 面试区分点 |
| --- | --- | --- |
| ACID | 原子性、一致性、隔离性和持久性的事务属性 | 业务约束和基础设施仍影响最终保证. [M10][M10] |
| MVCC | 多版本并发控制, 通过记录版本支持符合隔离规则的读取 | 不等于写入无锁. [M7][M7] |
| Read View | 一致性读用于判断记录版本可见性的视图 | 不是整库物理备份, RC 与 RR 的生成时机不同. [M1][M1] |
| Undo / Redo / Binlog | 分别服务于回滚与版本重建、InnoDB 崩溃恢复、服务端变更记录及复制恢复 | 三类日志不能相互替代. [M7][M7] [M9][M9] [M10][M10] |
| Record / Gap / Next-key Lock | 分别针对索引记录、索引间隙、记录与前方间隙的锁 | 锁定范围受索引、谓词和隔离级别影响. [M10][M10] |
| MDL | Metadata Lock, 协调对象访问与结构变更的元数据锁 | 与 InnoDB 行锁不是同一层机制. [M8][M8] |
| Purge | 清理已不再被回滚或一致性读需要的历史版本 | 事务提交不代表旧版本立刻物理删除. [M7][M7] |
| Covering Index | 查询所需数据可从所选索引取得, 减少额外取行 | 覆盖不代表扫描量小, 也不等于使用了最优索引. [M10][M10] |

### 索引与并发关键词补充

| 关键词 | 通俗解释与本篇场景 | 容易答错的地方 |
| --- | --- | --- |
| 聚簇索引 / 二级索引 | InnoDB 将行数据组织在聚簇索引中，二级索引记录包含定位所需的主键 | 通过二级索引取得其他列通常需要再访问聚簇索引，即“回表” |
| 最左前缀 | 联合索引按列的先后顺序组织；前导列条件影响连续查找范围 | 不代表缺少首列就绝不可能扫描该索引 |
| 选择性 / 基数 | 选择性通常关注条件筛掉多少数据；基数在索引统计中常指不同值数量的估计 | 高基数不保证某个具体条件命中行数少，数据可能倾斜 |
| ICP（Index Condition Pushdown） | 索引条件下推：先在存储引擎侧用索引列过滤，减少不必要的取行 | `Using index condition` 不等于覆盖索引的 `Using index` |
| RC / RR | Read Committed（读已提交）与 Repeatable Read（可重复读） | InnoDB 的一致性读与加锁读规则不同，不能把 RR 理解成所有查询永远读旧值 |
| 乐观锁 / 悲观锁 | 前者用版本等条件检测竞争，后者通过加锁协调访问 | 乐观锁失败要检查受影响行数；两者都需要定义失败后的业务行为 |
| 死锁 / 锁等待超时 | 前者存在相互等待的环，后者是等待超出配置期限 | 超时不必然说明有死锁；默认回滚范围也可能不同，见第 58 题 |
| 游标分页 | 用上一页稳定排序键定位下一段，如时间与主键的组合 | 不等同于数据库游标；并发插入、修改排序字段仍会影响结果 |
| DDL / DML | Data Definition Language 修改结构；Data Manipulation Language 操作数据 | 在线 DDL 不等于没有元数据锁或没有资源开销 |
